# QA-001 Defect List (D4)

ผลทดสอบอยู่ใน [qa-001-results.md](qa-001-results.md) ข้อบกพร่องด้านความปลอดภัยถือเป็น blocker **ไม่พบข้อบกพร่องด้านความปลอดภัย** ข้อสังเกตด้านล่างเป็นเรื่องความสามารถและประสบการณ์ผู้ใช้ ยังไม่มีข้อใดทำให้ข้อมูลรั่วหรือสตรีมบอกสำเร็จทั้งที่ไม่สมบูรณ์

| ID | ความรุนแรง | เจ้าของ | ข้อสังเกต | หลักฐาน | ข้อเสนอ |
| --- | --- | --- | --- | --- | --- |
| QA1-D01 | ปานกลาง | Backend (ตัดสินร่วมกับ Tech Lead) | **สตรีมที่หยุดนิ่งกลางทางรอจนหมดเวลารวมเท่านั้น** Backend มี timeout รวมอย่างเดียว (BE-004 บันทึกไว้เป็นข้อจำกัดที่ทราบ) ที่ค่าเริ่มต้น 180 วินาที ผู้ใช้อาจเห็นคำตอบค้างนานถึง 3 นาทีก่อนได้ `AI_TIMEOUT` | `QA1-E-e_timeout_gap` และ `_b`: ที่ timeout 3 วินาที ข้อผิดพลาดมาเมื่อครบ 3 วินาทีนับจากเริ่ม ไม่ใช่เมื่อไม่มีข้อมูลมาใหม่ | เพิ่ม timeout ของช่องว่างระหว่าง record (idle) แยกจากเวลารวม ตัวเลขควรมาจาก AI-006 (ช่องว่างปกติระหว่าง record ที่วัดได้) และกำหนดใน AI-007 |
| QA1-D02 | ปานกลาง | Backend / UI / AI-007 | **ผู้ใช้ไม่มีทางรู้ว่าคำขอกำลังรอคิว** Backend ส่ง `started` ทันทีที่รับคำขอ แม้ Ollama ยังไม่เริ่มงานเพราะรอคิว ผู้ใช้เห็นสถานะเหมือนกำลังตอบ ทั้งที่ยังไม่มี delta | `QA1-N-cold` (`started` ภายใน 0.1 วินาที ขณะที่ record แรกมาหลัง 2 วินาที), `QA1-E-queue-full` (คำขอที่รอคิวไม่ได้สัญญาณอะไรก่อน `AI_TIMEOUT`) | เพิ่ม event เช่น `queued` พร้อมลำดับ หรือ header ที่บอกตำแหน่งคิว หลัง BE-008 มีตัวจำกัดคำขอ (ตามแผน) เสนอใน AI-007 และ FE-004 |
| QA1-D03 | ต่ำ | Backend | Backend เก็บท้ายคำตอบราว 15 ตัวอักษรไว้ตรวจ `<think>` ที่ถูกแบ่งข้าม record จึงไม่ส่งข้อความล่าสุดสั้น ๆ จนกว่าจะมีข้อความมากขึ้นหรือคำตอบจบ ผลคือ `partial` เป็น false ได้ แม้ Ollama เริ่มตอบแล้ว | ดูส่วน "การบันทึกการแก้ Expected" ใน qa-001-results.md | ไม่ต้องแก้ ใช้เป็นข้อมูลให้ UI: อย่าใช้ `partial` เพื่อตัดสินว่ามีข้อความบนจอหรือไม่ ให้ใช้ข้อความที่ได้รับจริง |
