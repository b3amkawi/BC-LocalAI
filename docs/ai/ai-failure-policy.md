# AI Failure, Retry and Degradation Policy (AI-007 D1, D2, D4)

นโยบายนี้บอกว่าเมื่อ AI ล้มเหลวแต่ละแบบ ระบบควร **ตรวจจับอย่างไร, แจ้งผู้ใช้อย่างไร, ลองใหม่หรือไม่, บันทึกอะไร** โดยอิงผลทดสอบจริงใน [ai-failure-test-results.md](ai-failure-test-results.md) (จำลองความล้มเหลวกับ Ollama จริง 10 ชนิด ชนิดละ 6 ครั้ง) และผลของ Backend ใน [QA-001](../qa/qa-001-results.md)
รหัส error อ้างอิงของจริงใน `BC-LocalAI/Services/AiServiceException.cs` และ [BE-004 SSE contract](../BE-004-SSE-CONTRACT.md) ส่วนนี้เป็น **ข้อเสนอสำหรับ Backend Developer** ไม่ได้แก้โค้ดใน Issue นี้

ตัวเลขทั้งหมดวัดบน RTX 4050 Laptop 6 GB, Ollama 0.40.5, qwen3:4b ซึ่งไม่ใช่สเปกเป้าหมาย (RTX 4060/4070) จึงใช้เป็นทิศทาง

## 1. Failure matrix (D1)

| --- | --- | --- | --- | --- | --- | --- |
| 1 | Ollama ไม่ทำงาน | connection ถูกปฏิเสธ | `AI_UNAVAILABLE` | ได้ error ภายใน ≈ 2.05 วินาที (Windows ลองเชื่อมต่อซ้ำหนึ่งครั้ง) | หลังเริ่มบริการใหม่ ≈ 4 วินาทีจนรับคำขอ และคำขอแรกตอบได้ ≈ 7 วินาที (รวมโหลดโมเดล) | F03 |
| 2 | Ollama ถูกปิดกลางสตรีม | สตรีมจบโดยไม่มี `done` | `AI_INVALID_RESPONSE` (ข้อความที่ได้แล้วเป็นบางส่วน) | ข้อความค้างครึ่งทาง จากนั้นคำขอใหม่ได้ `AI_UNAVAILABLE` | ต้องมีตัวดูแล process เริ่มใหม่: ≈ 7 วินาทีถึงตอบได้ | F02 |
| 3 | runner ของโมเดลล้มกลางสตรีม | record `{"error": ...}` หลังได้ HTTP 200 | `AI_PROVIDER_ERROR` | ข้อความค้างครึ่งทาง | **ฟื้นเอง** ไม่ต้องเริ่ม Ollama ใหม่: คำขอถัดไปสำเร็จใน ≈ 4 วินาที (ต่ำสุด 3.7 สูงสุด 4.6) | F01 |

| 8 | response ไม่ถูกต้อง (JSON เสีย, โมเดลไม่ตรง, Content-Type ผิด, `<think>`) | Backend ตรวจรูปแบบ | `AI_INVALID_RESPONSE` | ได้ error ไม่มีข้อความรั่ว | ไม่เกี่ยวกับ Ollama ล้ม | QA-001 |

| 11 | โมเดลถูกยกเลิกการโหลด (cold start) | ไม่มี (ไม่ใช่ความล้มเหลว) | ไม่มี | คำขอแรกช้าลง: record แรก ≈ 2.9 วินาที (2.8 ถึง 3.1) เทียบ warm ≈ 40 มิลลิวินาที | - | F04 |
| 12 | สั่งยกเลิกการโหลดขณะสตรีมกำลังวิ่ง | ไม่มี | ไม่มี | **สตรีมที่วิ่งอยู่จบปกติ** (Ollama รอให้จบก่อนถอนโมเดล) คำขอถัดไปเป็น cold start ≈ 3 วินาที | - | F05 |
| 13 | หน่วยความจำไม่พอ | **ไม่ได้ inject** (เสี่ยงทำเครื่องค้าง) | คาดว่า `AI_PROVIDER_ERROR` หรือ `AI_UNAVAILABLE` | ไม่ทราบจากการวัด | ไม่ทราบ | ป้องกันด้วยนโยบายความจุ (ข้อ 4) |

หมายเหตุ: ค่า "คำขอที่ถูกทิ้งไม่ทำให้ช้า" ได้จากการรอคิวหลังคำขอที่ใช้เวลา ≈ 12.6 วินาที ไม่ใช่การรับประกันทุกกรณี และ Ollama 0.40.5 เท่านั้น

## 2. นโยบาย retry (D2)

หลักการ: Ollama ทำทีละคำขอ (AI-004) การลองใหม่เข้าคิวต่อท้ายและใช้ GPU ซ้ำ จึง **ไม่ retry อัตโนมัติ** ยกเว้นกรณีที่ปลอดภัยด้านล่าง ให้ผู้ใช้เป็นคนตัดสิน

| รหัส | retry อัตโนมัติ | ปุ่ม "ลองใหม่" | เหตุผลจากหลักฐาน |
| --- | --- | --- | --- |
| `AI_UNAVAILABLE` | **ไม่** | เปิดได้หลัง ≈ 10 วินาที | Ollama ใช้ ≈ 7 วินาทีจนตอบได้ ลองซ้ำที่ 2 วินาทีล้มซ้ำแน่นอน |
| `AI_PROVIDER_ERROR` | **ไม่** (ข้อความที่ส่งไปแล้วเป็นบางส่วน) | เปิดได้ทันที Ollama ฟื้นเองใน ≈ 4 วินาที จึงควรหน่วง ≈ 5 วินาที | กรณี runner ล้มเกิดหลังเริ่มตอบเสมอ การรันซ้ำอัตโนมัติจะซ้ำข้อความที่ผู้ใช้เห็นแล้ว |
| `AI_RESPONSE_TOO_LARGE` | **ห้าม** | เปิดได้แต่ต้องบอกให้ถามให้สั้นลง | ผลเดิมทุกครั้ง (F07: `temperature=0`) |
| `AI_INVALID_RESPONSE` | **ไม่** | เปิดได้ | สาเหตุอาจเป็น Ollama ถูกปิดกลางทาง (ฟื้นด้วยการรอ) หรือคำตอบผิดรูป (ลองซ้ำอาจได้ผลเดิม) ถ้าเกิดซ้ำ 3 ครั้งติดต่อกันให้ถือว่า AI ผิดปกติและหยุดรับคำขอใหม่ชั่วคราว |
| `AI_TIMEOUT` | **ไม่** | เปิดได้ แต่แจ้งว่าระบบกำลังคนแน่น | คำขอใช้เวลาเต็ม deadline แล้ว ลองซ้ำเท่ากับใช้ GPU ซ้ำสองเท่าและต่อคิวใหม่ |
| ยกเลิกโดย client | **ห้าม** | - | ผู้ใช้ตั้งใจหยุด |
| `INVALID_MESSAGE` | ไม่เกี่ยว (400 ก่อนเริ่มสตรีม) | - | - |

เงื่อนไขทั่วไป: ห้ามลองใหม่ถ้ามี delta ส่งไปแล้ว หรือผู้ใช้ยกเลิก หรือรหัสคือ `AI_RESPONSE_TOO_LARGE`

## 3. Degradation และ fallback (D2)

**ทำได้โดยไม่ต้องขออนุมัติ**
- แสดงข้อความแนะนำให้ถามสั้นลง/ลองใหม่ภายหลัง
- ปิดปุ่มลองใหม่ชั่วคราวขณะบริการไม่พร้อม โดยตรวจสถานะ (`GET /api/version` ของ Ollama ผ่าน Backend) ทุก ≈ 5 วินาที
- จำกัดความยาวข้อความที่รับ (ตัวเลขจาก AI-008) และจำกัดคำขอต่อผู้ใช้ (ข้อ 4)
- บันทึกรหัส เหตุผลสั้น ๆ และเวลา (ห้ามบันทึกคำถามหรือคำตอบ)

**ต้องได้รับอนุมัติเป็นลายลักษณ์อักษรจาก Leader ก่อน**
- เปลี่ยนโมเดลหรือเพิ่มโมเดลสำรอง
- ลดคุณภาพคำตอบ (เช่นลด `num_predict` ลงโดยไม่บอกผู้ใช้)
- ส่งคำถามไปบริการ AI ภายนอก ซึ่งขัดกับหลักการใช้ AI ในเครื่อง
- เปลี่ยนค่า configuration ของ Ollama บนระบบจริง (เช่น `OLLAMA_NUM_PARALLEL`)

**ห้ามมี fallback ที่เปลี่ยนโมเดลหรือส่งข้อมูลออกนอกเครื่องโดยไม่แจ้งผู้ใช้**

## 4. นโยบายคิวและผู้ใช้หลายคน (D2, ข้อเสนอสำหรับ BE-008)

Ollama ตอบทีละคำขอ คำขอที่รอคิวไม่มีสัญญาณอะไร (QA1-D02) ข้อเสนอ:

| กรณี | รหัส HTTP | ข้อความ | บอกเวลาลองใหม่ |
| --- | --- | --- | --- |
| ผู้ใช้คนเดียวมีคำขอค้างเกินโควตา (ข้อเสนอเริ่มต้น: 1 คำขอที่กำลังทำงานต่อผู้ใช้) | **429** | ข้อความ "มีคำถามที่กำลังตอบอยู่" | ใช่ |
| คิวรวมของระบบเต็ม (ข้อเสนอเริ่มต้น: คำขอที่รอรวมไม่เกิน 8) | **503** | ข้อความ "ระบบกำลังมีผู้ใช้จำนวนมาก" | ใช่ |

- ตัวเลข 8 เป็นข้อเสนอเริ่มต้นที่ต้องยืนยันด้วยผล AI-006: เวลารอที่ผู้ใช้ยอมรับได้ ≈ 30 วินาที หารด้วยเวลาให้บริการต่อคำถาม (medium ≈ 1.4 วินาที, long ≈ 3.4 วินาที) ได้ราว 21 ถึง 9 คำขอ
- คำขอที่ผู้ใช้ปิดหน้าไปแล้วต้องถูกยกเลิกถึง Ollama ทันที (Backend ทำแล้ว: Ollama รู้ภายใน ≈ 0.2 วินาทีใน QA-001) และคำขอที่ถูกทิ้งขณะรอคิวไม่กินเวลา (F10)
- ควรเพิ่ม event `queued` พร้อมลำดับให้ UI แสดงสถานะรอคิว (QA1-D02)
- การ implement ตัวจำกัดคำขอเป็นงานของ Backend Issue (ตามแผนเรียก BE-008) Issue นี้ให้นโยบายและตัวเลขเท่านั้น และรหัส 429/503 นี้ต้องได้รับการยืนยันจากทีม Backend

## 5. ข้อความที่แสดงผู้ใช้ (D4)

ข้อความต้องไม่มีรายละเอียดภายใน (พอร์ต, path, ชื่อ process, stack) และไม่แสดงข้อความดิบที่ Ollama ส่งมา

| รหัส | ข้อความภาษาไทย |
| --- | --- |
| `AI_UNAVAILABLE` | ตอนนี้ระบบ AI ยังไม่พร้อมใช้งาน กรุณาลองใหม่อีกครั้งในอีกสักครู่ |
| `AI_PROVIDER_ERROR` | ระบบ AI ขัดข้องระหว่างตอบ กรุณากดลองใหม่ |
| `AI_RESPONSE_TOO_LARGE` | คำตอบยาวเกินขีดจำกัด ลองถามให้สั้นลงหรือแบ่งเป็นหลายคำถาม |
| `AI_INVALID_RESPONSE` | ได้รับคำตอบที่ไม่สมบูรณ์ กรุณาลองใหม่ |
| `AI_TIMEOUT` | ใช้เวลานานเกินไป ตอนนี้อาจมีผู้ใช้จำนวนมาก กรุณาลองใหม่ภายหลัง |
| 429 | คุณมีคำถามที่กำลังตอบอยู่ กรุณารอให้เสร็จก่อนถามคำถามถัดไป |
| 503 (คิวเต็ม) | ตอนนี้มีผู้ใช้จำนวนมาก กรุณาลองใหม่ในอีกสักครู่ |

ถ้ามีข้อความบางส่วนแสดงแล้วเกิด error ให้เก็บข้อความนั้นไว้และแสดงข้อความ error ต่อท้าย พร้อมระบุว่าเป็นคำตอบที่ไม่สมบูรณ์ ห้ามนับเป็นคำตอบเสร็จ (สอดคล้อง BE-004: ไม่ส่ง `completed` หลัง error)

## 6. Handoff สำหรับ Backend และ UI (D4)

**Backend (BE-004 / BE-008)**
1. ใช้ตารางข้อ 2 เป็นกติกา retry ไม่เพิ่ม retry อัตโนมัติ
2. เพิ่ม timeout ของ **ช่องว่างระหว่าง record** แยกจากเวลารวม (QA1-D01) ตัวเลขเริ่มต้นเสนอ 30 วินาที (record ปกติมาทุกไม่กี่ร้อยมิลลิวินาที และสิ่งที่รอนานที่สุดก่อน record แรกที่วัดได้คือ cold start ≈ 3 วินาที (AI-006 จะวัดช่องว่างระหว่าง record โดยตรงเพื่อยืนยัน)) ต้องทดสอบก่อนใช้
3. ตัวจำกัดคำขอและคิวตามข้อ 4 พร้อม event `queued`
4. log เฉพาะ: รหัส error, เหตุผลสั้น ๆ, เวลาที่ใช้, จำนวน token ห้ามมีคำถาม คำตอบ หรือข้อความดิบจาก Ollama (QA-001 ยืนยันว่า Backend ปัจจุบันทำตามนี้แล้ว)
5. ห้ามส่งต่อข้อความ `upstream_error` ของ Ollama ให้ผู้ใช้ (มีชื่อ endpoint ภายในเช่นที่พบใน F01)

**UI (FE-002 / FE-004)**
1. ใช้ข้อความข้อ 5 เป็นค่าเริ่มต้น
2. ปุ่มลองใหม่ตามตารางข้อ 2 (หน่วงตามที่กำหนด)
3. เก็บข้อความบางส่วนเมื่อเกิด error
4. แสดงสถานะรอคิวเมื่อ Backend ส่ง `queued`

## 7. ข้อจำกัดของการทดสอบ
- ไม่ได้ inject หน่วยความจำไม่พอ
- ทดสอบบน Ollama 0.40.5 บน Windows เท่านั้น พฤติกรรมอาจต่างในรุ่นอื่น (เช่นเวลา connection ถูกปฏิเสธ ≈ 2.05 วินาทีเป็นผลของ Windows)
- instance ที่ inject เป็น instance แยก พฤติกรรมการฟื้นของบริการที่ติดตั้งเป็น Windows Service ยังไม่ได้ทดสอบ
- ตัวเลขคิวเริ่มต้นรอยืนยันด้วย AI-006 และเครื่องเป้าหมาย
