## 2. วิธีประมาณโทเคน (D2)

ใช้ตัวประมาณของ BE-007 หลังแก้ในรอบ review (`Utf8TokenEstimator`: ตัวเลขและสัญลักษณ์ ASCII = 1 โทเคน, ตัวอักษร ASCII = 0.5, อักขระอื่น = 1 ต่อ 3 ไบต์ UTF-8, บวก 4 ต่อข้อความ) ใน 30 จุดวัด ค่าจริงไม่เคยเกินค่าประมาณ (อัตรา จริง/ประมาณ ≤ 1.00) ประมาณเกินจริงสูงสุดในข้อความอังกฤษ ≈ 3.4 เท่า (ปลอดภัยแต่เก็บประวัติได้น้อยกว่าที่พอดี) ไม่ใช่การรับประกันสำหรับทุกข้อความ ดู [BE-007-AI-REVIEW.md](../chat-history/BE-007-AI-REVIEW.md)
ค่าต่ำสุดที่ใช้ตรวจการตัดคือ ไบต์ ÷ 6.5 (ไม่เคยพบข้อความที่ใช้โทเคนน้อยกว่านี้)

## 3. งบประวัติสนทนา (D3)

เพดานทั้งหมดต่อคำขอ: `context 4096 − MaxOutputTokens 1024 − overhead (system + template ≈ 100)` ≈ **2,900 โทเคนที่ประมาณได้**

| ส่วน | งบ | กติกา |
| --- | --- | --- |
| คำถามใหม่ | ≤ 1,200 (`ChatHistory:MaxQuestionTokens`) | เกินแล้ว 400 `QUESTION_TOO_LONG` ไม่บันทึก ไม่ส่งเข้าโมเดล |
| ประวัติ | ≤ 1,500 (`ContextTokenBudget`) | เก็บคู่ถามตอบที่ **ครบและ completed** จากใหม่ไปเก่า ตัดเก่าก่อน ไม่ตัดกลางคู่ ไม่ใช้ข้อความ failed/cancelled |
| ผลรวม | `ContextTokenBudget + MaxQuestionTokens ≤ 2900` | ตรวจตอนเริ่มระบบ |
| ลำดับความสำคัญ | system prompt, คำถามใหม่ > ประวัติใหม่ > ประวัติเก่า | ประวัติเก่าถูกตัดก่อนเสมอ |
| แจ้งผู้ใช้ | เมื่อประวัติถูกตัด UI ควรแสดงว่า "ระบบจำบทสนทนาย้อนหลังได้ไม่ครบ" (ยังไม่มีสัญญาณนี้ใน API: เสนอให้ BE-007 ส่ง `contextDroppedMessages` ใน response ซึ่ง `ConversationContext.DroppedMessages` มีค่าอยู่แล้ว) | |

ไม่ใช้การสรุปบทสนทนาอัตโนมัติ (นอกขอบเขต) ถ้าต้องการจำนานขึ้นให้ดูข้อ 6

## 4. กติกาจำกัด input ชั่วคราวและตรวจจับการตัด (D4, 3.6)

**กติกา A (กันก่อนส่ง):** ปฏิเสธเมื่อ `ประมาณ(prompt ทั้งก้อน) > 2,900` ด้วย 400 และข้อความที่เข้าใจได้ (ใช้อยู่แล้วกับคำถามผ่าน MaxQuestionTokens)
**กติกา B (ตรวจหลังตอบ ใช้ `prompt_eval_count` ของเรกคอร์ดสุดท้าย):**
1. `|prompt_eval_count − (ctx/2 + 2)| ≤ 10` และ `ไบต์ของ prompt ÷ 6.5 > ctx/2 + 152` → **ถูกตัดแน่นอน** ให้บันทึก error/log และไม่เก็บคำตอบเป็น completed
2. `prompt_eval_count > ctx − 64` → **เสี่ยงข้อมูลหายแม้ไม่ถูกตัด** (ที่ว่างให้คำตอบน้อยเกินไป) ให้บันทึกคำเตือน
ผลทดสอบ: กติกา B-1 ตรวจจับได้ **81 จาก 81** การรันที่ถูกตัด (4096) และ 9 จาก 9 (8192) และเตือนผิด **0 ครั้ง** จาก 297 + 36 การรัน กติกา B-2 ทดสอบเฉพาะจุดขอบ (4,088 โทเคน) ซึ่งเป็นกรณีเดียวที่ B-1 พลาด
ข้อจำกัด: กติกา B ต้องรู้ `ctx` ที่ใช้จริง (อ่านได้จาก `/api/ps` ฟิลด์ `context_length`) และใช้ได้เมื่อ Backend เห็น `prompt_eval_count` (non-stream ตอนนี้ และเรกคอร์ดสุดท้ายของ stream)

## 5. สัญญา multi-turn (3.7)

ทดสอบ 3 ตา (ไทย/อังกฤษ) เทียบ (ก) prompt เดียวตาม template ของ BE-007 ผ่าน `/api/generate` กับ (ข) `/api/chat messages` ที่คง `format` และ `think:false` (คำตอบก่อนหน้าส่งเป็น `{"answer": ...}`)
ผล: **ทั้งสองวิธีจำข้อมูลจากตาก่อนหน้าได้ 100%** (30 จาก 30 ต่อวิธี) ข้อสรุป: คง prompt เดียวตาม template ปัจจุบัน (ไม่ต้องเปลี่ยนสัญญา AI-002) ข้อจำกัด: เคสทดสอบง่าย (ข้อเท็จจริงสั้น ไม่มีตัวรบกวน ประวัติ 2 ตา) ยังไม่ได้วัดกับประวัติยาวที่มีข้อมูลใกล้เคียงกันหลายชุด

## 6. ข้อเสนอเรื่อง context ที่ใหญ่ขึ้น (3.5, ให้ Leader ตัดสิน)

วัดบน instance แยก `OLLAMA_CONTEXT_LENGTH=8192` (ไม่แตะ config จริง):

| ตัวชี้วัด | 4096 | 8192 |
| --- | ---: | ---: |
| VRAM หลังโหลดโมเดล | 3,254 MB | 3,920 MB (+666) |
| cold start | 3.79 s | 3.82 s |
| prefill (โทเคน/วินาที, prompt 1k / 3k) | 3,379 / 3,235 | 3,387 / 3,261 |
| prompt อ่านครบสูงสุด / ถูกตัดตั้งแต่ | ≈ 4,061–4,084 / 4,160 | ≈ 7,961–8,000 / 8,260 |

ใช้ VRAM 3.9 GB จาก 6.1 GB จึงรองรับได้บนเครื่องนี้ ความเร็ว prefill เท่าเดิม ข้อดีคือเพิ่มงบประวัติได้ (เช่น ContextTokenBudget 1500 → ≈ 5,000) ข้อควรระวัง: VRAM เพิ่มตามจำนวน slot (ยังไม่ได้วัด 8192 ร่วมกับ NUM_PARALLEL=2), เครื่องเป้าหมายอาจต่าง **ยังไม่แนะนำให้เปลี่ยนจนกว่ามีความต้องการประวัติยาวจริง** ถ้าเปลี่ยน ต้องปรับ MaxQuestionTokens/ContextTokenBudget ให้ผลรวม ≤ ctx − 1024 − 100 และวัดซ้ำ

## 7. Handoff สำหรับ BE-007 (D6)
1. คงค่าเริ่มต้น `ContextTokenBudget=1500`, `MaxQuestionTokens=1200` (ผลรวม 2,700 ≤ 2,900) — ใน main แล้ว
2. เพิ่มกติกา B-1/B-2 ที่ Backend หลังได้ `prompt_eval_count` (ยังไม่มีใน BE-007) และส่ง `contextDroppedMessages` ให้ UI
3. อย่าเปลี่ยน `num_ctx` ในคำขอต่อคำขอ (การเปลี่ยน context ทำให้ Ollama โหลดโมเดลใหม่ ช้า) กำหนดที่ระดับ service เท่านั้น
