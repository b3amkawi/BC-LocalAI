# อ่านงาน AI-001–003 ตั้งแต่พื้นฐาน: ศัพท์ ตัวอย่าง และวิธีอธิบายให้ทีมฟัง

ฉบับนี้ขยายจาก [คู่มือส่งต่องาน](ai-001-003-handoff.md) สำหรับคนที่ยังไม่คุ้นศัพท์เทคนิค อ่านตามลำดับได้โดยไม่ต้องจำคำสั่งทั้งหมด ตัวอย่าง JSON ที่เขียนว่า “ตัวอย่าง” ใช้อธิบายรูปแบบ ไม่ใช่การอ้างว่าเพิ่งทดสอบใหม่ ผลจริงให้อ่านจาก [รายงาน AI-003](chat-evaluation-results.md) และไฟล์หลักฐานที่รายงานเชื่อมไว้

> **อัปเดต 20 ตุลาคม 2026:** ผล AI-003 ล่าสุดคือ **160/160 ผ่าน exit code 0** หลังเปลี่ยนการตรวจคำตอบจาก `expected_regex` เป็น `accepted_answers` แบบตรงทั้งคำตอบที่ต้องทำตามคำสั่งใน prompt (dataset version 3) ตัวเลข 141/160, HTTP 502 สามข้อ และคำอธิบาย regex/contradiction ในเอกสารนี้เป็น **ผลรอบ dataset version 2 ที่ถูกแทนแล้ว** ให้ยึด [รายงาน AI-003](chat-evaluation-results.md) เป็นผลปัจจุบัน

ถ้ามีเวลาอ่านน้อย ให้เริ่มข้อ 1–3 เพื่อรู้ว่าระบบทำงานอย่างไร ต่อด้วยข้อ 6–9 เพื่อรู้ว่าแต่ละ Issue พิสูจน์อะไร และข้อ 14 สำหรับซ้อมตอบพี่ ส่วนข้อ 4–5 และ 10–13 ใช้เปิดหาความหมายของศัพท์

## 1. งานของเราสามช่วงต่อกันอย่างไร

สมมติผู้ใช้ถามว่า **“หนึ่งบวกหนึ่งได้เท่าไร”** เราต้องพิสูจน์คนละเรื่องในแต่ละงาน:

| งาน | คำถามที่งานนั้นต้องตอบ | ถ้าทำสำเร็จ แปลว่าอะไร |
| --- | --- | --- |
| AI-001 | เครื่องนี้ติดตั้งและเรียกโมเดลได้หรือยัง | โปรแกรมและโมเดลพร้อมให้ทดลอง มีวิธีติดตั้งและตรวจพื้นฐาน |
| AI-002 | โปรแกรม Backend ต้องส่งอะไร และเชื่อข้อมูลที่รับมาได้เมื่อไร | มีข้อตกลงรูปแบบข้อมูล วิธีตรวจ และการจำแนกความล้มเหลว |
| AI-003 | เมื่อเรียกผ่าน Backend แล้ว คำตอบที่ได้มีคุณภาพตามเกณฑ์หรือไม่ | มีผลทดสอบทั้งเส้นทาง แยกได้ว่าข้อไหนผ่าน ข้อไหนผิด และผิดอย่างไร |

ตัวอย่างที่ช่วยแยกสามเรื่องนี้: เครื่องอาจเรียกโมเดลได้แล้วใน 001, โมเดลส่ง `{"answer":"0"}` ได้ตรงรูปแบบใน 002 แต่ถ้าคำถามคือ `1 - 9` คำตอบนั้นยังผิดเนื้อหาใน 003 เพราะควรเป็น `-8`

ดังนั้น “ติดตั้งได้”, “ข้อมูลถูกโครงสร้าง” และ “ตอบถูก” เป็นสามเงื่อนไขที่ต้องตรวจแยกกัน

## 2. ใครทำหน้าที่อะไรในระบบ

### Ollama, Qwen3:4b และการประมวลผล

**Ollama** คือโปรแกรมที่ใช้จัดการและรันโมเดลในเครื่อง ในงานนี้เราเรียกมันว่า **AI runtime** หมายถึงซอฟต์แวร์ที่ทำให้โมเดลทำงานและรับคำขอได้ ตัว Ollama มีทั้งคำสั่งใน terminal และ HTTP API ให้โปรแกรมอื่นเรียก

**Qwen3:4b** คือโมเดลที่ Ollama นำมารัน เป็นตัวที่ประมวลผลคำถามแล้วสร้างคำตอบ ชื่อ `qwen3:4b` ใช้ระบุรุ่นโมเดลให้ตรงกัน โดย `4b` เป็นชื่อรุ่นขนาดประมาณสี่พันล้านพารามิเตอร์ ไม่ได้แปลว่าใช้ RAM 4 GB พอดี และไม่ใช่เลขเวอร์ชันของ Ollama

**Parameter — พารามิเตอร์** ในคำว่าโมเดลสี่พันล้านพารามิเตอร์ หมายถึงค่าตัวเลขภายในโมเดลที่ได้จากการฝึก ไม่ใช่จำนวนคำถามที่โมเดลจำได้ ส่วนคำว่า parameter ในคำสั่ง PowerShell เช่น `-TimeoutSec` หมายถึงตัวเลือกที่ส่งให้สคริปต์ ต้องดูบริบทของคำเดียวกัน

**LLM — Large Language Model** คือโมเดลภาษาขนาดใหญ่ที่สร้างข้อความจากบริบทที่ได้รับ การที่มันเขียนได้คล่องไม่ได้รับประกันว่าข้อมูลหรือการคำนวณจะถูกทุกครั้ง

**Inference — อินเฟอเรนซ์** คือการนำโมเดลที่มีอยู่มาตอบคำถาม ส่วน **training/fine-tuning** คือการฝึกหรือปรับน้ำหนักโมเดล งาน 001–003 ของเราใช้ inference ไม่ได้ fine-tune โมเดล

วิธีอธิบายให้พี่ฟัง: “Ollama เป็นโปรแกรมที่รัน ส่วน Qwen เป็นโมเดลที่ใช้ตอบครับ ต้องระบุทั้ง runtime version และ model เพื่อให้รู้ว่าทดสอบชุดไหน”

### Backend, Controller, Service และ UI

**Backend — แบ็กเอนด์** คือโปรแกรมที่รับคำขอ ตรวจข้อมูล เรียกส่วนอื่น และส่งผลกลับ ในโปรเจกต์นี้ใช้ ASP.NET Core/.NET และมีทางเข้า `/api/chat`

**Controller — คอนโทรลเลอร์** คือส่วนรับคำขอจาก API เช่น `ChatController` รับข้อความ ตรวจว่าข้อความไม่ว่าง แล้วส่งต่อให้ส่วนบริการ

**Service — เซอร์วิส** คือส่วนที่รับผิดชอบงานเฉพาะ เช่น `OllamaAIService` ติดต่อ Ollama และตรวจผลตาม contract ส่วน `IAIService` เป็น interface หรือข้อตกลงในโค้ดว่าบริการ AI ต้องมีความสามารถอะไร ให้ Controller เรียกผ่านข้อตกลงนี้ได้

**Frontend/UI — หน้าจอผู้ใช้** คือหน้าที่คนพิมพ์และอ่านคำตอบ งาน AI-003 ของเราทดสอบถึง Backend API ยังไม่ใช่การทดสอบหน้าเว็บใน browser และไม่ได้สร้าง Web UI

**Provider — โพรไวเดอร์** คือบริการที่ Backend เรียกเพื่อขอคำตอบ ในบริบทนี้หมายถึง Ollama ไม่ได้หมายถึงบริษัทอินเทอร์เน็ตหรือ Wi-Fi

ฝ่าย AI ทำคู่มือ, contract, ชุดคำถาม และการประเมิน ฝ่าย Backend เป็นเจ้าของ Controller/service และการแปลง error อย่าอธิบายว่าเราเขียน Backend ทั้งหมดเพียงเพราะมีไฟล์เหล่านั้นใน Repository

## 3. ไล่หนึ่งคำถามให้เห็นข้อมูลทั้งเส้นทาง

ลำดับย่อ:

```text
สคริปต์ทดสอบ
  -> Backend /api/chat
  -> Ollama /api/generate
  -> Qwen3:4b สร้างคำตอบ
  -> Backend ตรวจและแปลงข้อมูล
  -> สคริปต์ตรวจคำตอบและเก็บหลักฐาน
```

**ขั้นที่ 1 — ส่งให้ Backend:** ตัวอย่าง body ที่ส่งไป `http://localhost:5290/api/chat`

```json
{"message":"หนึ่งบวกหนึ่งได้เท่าไร ตอบสั้น ๆ"}
```

**ขั้นที่ 2 — Backend ส่งให้ Ollama:** Backend นำข้อความไปใส่ `prompt` พร้อม model, system prompt, schema และ options ตาม AI-002 แล้วส่งไป `http://127.0.0.1:11434/api/generate`

**ขั้นที่ 3 — Ollama ตอบ:** ตัวอย่างข้อมูลที่มีสองชั้น

```json
{
  "model": "qwen3:4b",
  "response": "{\"answer\":\"2\"}",
  "done": true,
  "done_reason": "stop"
}
```

**ขั้นที่ 4 — Backend parse และ validate:** อ่าน JSON ชั้นนอก แล้วนำข้อความใน `response` ไปอ่านเป็น JSON อีกครั้ง จึงได้ object `{"answer":"2"}` จากนั้นตรวจว่าครบเงื่อนไขทั้งหมด

**ขั้นที่ 5 — Backend ตอบผู้เรียก:** ตัวอย่าง public API response

```json
{"response":"2","model":"qwen3:4b"}
```

สังเกตว่าชื่อ `response` พบทั้งสองฝั่งแต่เก็บคนละรูปแบบ ฝั่ง Ollama เก็บข้อความ JSON ที่ต้อง parse อีกชั้น ส่วนฝั่ง Backend เก็บข้อความคำตอบสุดท้าย

คำว่า **“ไม่มี JSON ซ้อนให้ผู้ใช้เห็น”** จึงหมายถึงข้อความคำตอบไม่ควรเป็น `{"answer":"2"}` แต่ควรเป็น `2` ส่วน HTTP body ของ Backend ยังคงเป็น JSON ได้ตามปกติ

AI-001/002 เรียก Ollama โดยตรงได้เพื่อพิสูจน์ runtime/contract ส่วน AI-003 ต้องเข้าทาง Backend เพื่อให้ตรวจทั้งเส้นทาง ถ้าข้าม Backend จะยังไม่พิสูจน์การเชื่อมต่อของ Backend

## 4. ศัพท์เกี่ยวกับ API และเครือข่าย

### API, REST API และ Endpoint

**API — เอพีไอ** คือช่องทางที่โปรแกรมใช้คุยกันตามรูปแบบที่ตกลงไว้ ในงานนี้สคริปต์คุยกับ Backend และ Backend คุยกับ Ollama ผ่าน HTTP

**REST API** เป็นแนวทางหนึ่งในการออกแบบ API บน HTTP ในงานที่ได้รับมอบหมายใช้คำนี้เรียกการส่งข้อมูลไปยัง endpoint เพื่อรับคำตอบ การส่ง HTTP/JSON ได้เพียงอย่างเดียวไม่ได้อธิบายคุณสมบัติ REST ทั้งหมด แต่เพียงพอให้เข้าใจช่องทางที่งานนี้ใช้

**Endpoint — เอนด์พอยต์** คือจุดที่เรียกใช้งาน ระบุทั้งวิธีเรียกและ URL เช่น `POST http://localhost:5290/api/chat`

แยก URL นี้อ่านได้ว่า:

| ส่วน | ตัวอย่าง | ความหมาย |
| --- | --- | --- |
| scheme | `http://` | วิธีสื่อสารที่ใช้ |
| host | `localhost` | เครื่องปลายทาง ในที่นี้คือเครื่องที่กำลังรันคำสั่ง |
| port | `5290` | หมายเลขช่องรับของบริการบนเครื่องนั้น |
| path/route | `/api/chat` | เส้นทางงานที่เรียกในบริการ |

**BaseUrl** คือส่วนฐาน เช่น `http://localhost:5290` แล้วค่อยต่อ path เป็น `/api/chat` โปรเจกต์มีสองบริการจึงใช้คนละ port: Backend `5290`, Ollama `11434`

**Loopback — ลูปแบ็ก** คือที่อยู่สำหรับติดต่อกลับเข้าเครื่องตัวเอง ตัวอย่างที่ contract อนุญาตคือ `127.0.0.1`, `localhost`, `[::1]` ถ้าเพื่อนเรียก `localhost` จากเครื่องเพื่อน จะหมายถึงเครื่องเพื่อน ไม่ได้วิ่งมาที่เครื่องเรา

`192.168.x.x` เป็นตัวอย่าง private network IP ใช้ระบุเครื่องในเครือข่ายได้ แต่ไม่ใช่ loopback จึงไม่ผ่านข้อกำหนด Ollama BaseUrl ของงานนี้ ฝ่าย Backend ต้องตรวจด้วย `Uri.IsLoopback` ไม่ใช่แค่เช็กว่าข้อความ URL มีคำว่า localhost อยู่ข้างใน

Loopback ช่วยจำกัดปลายทางของการเรียกในเครื่องตามงานนี้ ไม่ได้พิสูจน์ว่าทั้งเครื่องไม่มีโปรแกรมอื่นส่งข้อมูลออกอินเทอร์เน็ต

การตรวจ BaseUrl ด้วย `Uri.IsLoopback` ตรวจว่า Backend กำลังจะเรียกไปที่ไหน ส่วน **listener/bind** คือการตั้งว่าบริการเปิดรับคำขอจากที่อยู่ใด ต้องตรวจการตั้งค่าและช่องรับของ Ollama แยกหากจะยืนยันว่า “รับผ่าน loopback เท่านั้น” แค่ Backend เรียก 127.0.0.1 ไม่ได้พิสูจน์ว่า Ollama ไม่เปิดรับจากเครือข่ายอื่นด้วย

### Request, Response, Header และ Body

**Request — รีเควสต์** คือคำขอที่ส่งออก เช่น “ช่วยตอบคำถามนี้” **Response — รีสปอนส์** คือสิ่งที่บริการส่งกลับ ทั้งข้อมูลคำตอบหรือข้อมูล error

**Header** คือข้อมูลกำกับคำขอ เช่น `Content-Type: application/json; charset=utf-8` บอกชนิดและ encoding ของ body ส่วน **body/payload** คือเนื้อหาที่ส่ง เช่น `{"message":"สวัสดี"}`

**UTF-8** คือวิธีเข้ารหัสตัวอักษรเป็น bytes เพื่อส่งหรือเก็บข้อมูล รองรับไทย อังกฤษ และ Emoji ต้องใช้ให้ตรงทั้งข้อความจริงกับ header ไม่อย่างนั้นอาจได้อักษรเพี้ยนแม้ request ไปถึง

**GET** ใช้อ่านข้อมูล เช่น `GET /api/version` ดูเวอร์ชัน Ollama **POST** ใช้ส่งข้อมูลให้ปลายทางประมวลผล เช่น `POST /api/chat` พร้อมคำถาม การเปิด URL ในแถบ browser ตามปกติเป็น GET จึงไม่เท่ากับส่ง POST พร้อม JSON body

`GET /api/version` ผ่านยืนยันว่า endpoint ตอบข้อมูลเวอร์ชันได้ ยังไม่ยืนยันว่าโมเดลติดตั้ง โหลดเข้าหน่วยความจำ หรือสร้างคำตอบสำเร็จแล้ว ต้องทดสอบขั้นถัดไป

### HTTP status และการเชื่อมต่อไม่สำเร็จ

| คำที่พบ | อ่านผลอย่างไรในงานนี้ |
| --- | --- |
| HTTP 200 | บริการตอบสำเร็จระดับ HTTP ยังต้องตรวจรูปแบบและความถูกต้องของคำตอบ |
| HTTP 400 | ตัวอย่างเช่น Backend ปฏิเสธ message ที่ว่าง เป็นปัญหาคำขอที่ต้องแก้ |
| HTTP 502 + `AI_INVALID_RESPONSE` | Backend แจ้งว่าคำตอบจากผู้ให้บริการไม่ผ่านการตรวจ ในหลักฐาน AI-003 พบ 3 ข้อ |
| HTTP 504 | ใช้สื่อปัญหารอบริการปลายทางที่ Backend เรียก เช่น Ollama ไม่ทันตามการจัดการของ Backend อย่าเหมารวมคนกดยกเลิกเป็นกรณีนี้ |
| connection refused / unable to connect | ติดต่อบริการไม่ได้ ยังอาจไม่มี HTTP response เลย จึงไม่ควรเรียกทุกครั้งว่า HTTP 500 |

**Error mapping** คือการที่ Backend แปลงสาเหตุภายในเป็น HTTP status และ error code สำหรับผู้เรียก การกำหนด mapping จริงเป็นงาน Backend ส่วน AI-002 กำหนด classification หรือประเภทของปัญหาให้ทีมใช้ร่วมกัน

## 5. JSON, Schema, Parse และ Validation ต่างกันอย่างไร

**JSON — เจสัน** เป็นรูปแบบข้อความสำหรับแลกข้อมูล เช่น `{"answer":"2"}` ใน object นี้ `answer` คือ **key/field/property** หรือชื่อช่องข้อมูล ส่วน `"2"` คือ value หรือค่าของช่องนั้น

| รูปแบบ | ชนิดข้อมูล | สิ่งที่ต้องเข้าใจ |
| --- | --- | --- |
| `"2"` | string | ข้อความตัวเลข ยังเป็นข้อความ |
| `2` | number | ค่าตัวเลข |
| `true` / `false` | boolean | ค่าจริง/เท็จ ไม่ใส่เครื่องหมายคำพูด |
| `"true"` | string | ข้อความว่า true ไม่ใช่ boolean |
| `{"answer":"2"}` | object | กลุ่มข้อมูลที่อ้างค่าด้วยชื่อ field |
| `["2","3"]` | array | รายการข้อมูลหลายตัว |
| `null` | null | ค่าไม่มีข้อมูล ไม่ใช่ string ว่าง |

**Parse — พาร์ส** คืออ่านข้อความตามกติกาของ JSON แล้วแปลงเป็นข้อมูลที่โปรแกรมเข้าถึง field และตรวจชนิดได้ ถ้า JSON ผิดกติกาจะ parse ไม่สำเร็จ ตัวอย่าง malformed JSON คือ `{"answer":}` ซึ่งไม่มีค่าหลัง colon

**Serialize — ซีเรียลไลซ์** คือแปลงข้อมูลในโปรแกรมกลับเป็นข้อความ JSON เช่น `ConvertTo-Json` ส่วน `ConvertFrom-Json` ทำทางกลับ `JsonDocument` เป็น parser ที่เราใช้ตรวจโครงสร้างและชื่อ field รวมถึงชื่อที่ซ้ำกัน

เครื่องหมาย `\"` ในตัวอย่าง Ollama response หมายถึงการ escape เครื่องหมายคำพูดให้อยู่ภายใน string ได้ จึงเห็น `"response":"{\"answer\":\"2\"}"` ไม่ใช่ให้ผู้ใช้พิมพ์ backslash เพิ่มเองทุกครั้ง ใช้ JSON serializer สร้างข้อมูลจะลดความผิดพลาดจากการต่อข้อความมือ

**Schema — สคีมา** คือกติกาของรูปแบบข้อมูล เช่น ต้องเป็น object, มี `answer` เป็น string และห้าม field อื่น **Structured output** คือการขอให้โมเดลสร้างคำตอบตามรูปแบบนั้น

ตัวอย่างกติกา AI-002:

```json
{
  "type": "object",
  "properties": {"answer": {"type": "string"}},
  "required": ["answer"],
  "additionalProperties": false
}
```

- `type: object` หมายถึงข้อมูลชั้นนั้นต้องเป็น object
- `properties` บอก field ที่อนุญาตและชนิดของมัน
- `required` บอก field ที่ห้ามขาด
- `additionalProperties: false` ห้ามเพิ่ม field อื่น เช่น `reasoning`

**Validation — แวลิเดชัน** คือการตรวจว่าข้อมูลที่ได้รับตรงกติกาจริง ไม่ใช่เชื่อว่าเคยส่ง schema ไปแล้วจึงต้องถูกเสมอ

ตัวอย่างต่อไปนี้อาจ parse เป็น JSON ได้ แต่ยังไม่ผ่าน contract:

| คำตอบ | เหตุผลที่ไม่ผ่าน |
| --- | --- |
| `{"answer":2}` | ต้องการ string แต่ได้ number |
| `{"answer":"   "}` | หลังตัดช่องว่างไม่มีคำตอบ |
| `{"answer":"2","extra":"x"}` | มี field เกิน |
| `{"Answer":"2"}` | ตัวพิมพ์ไม่ตรง `answer` |
| `{"answer":"one","answer":"two"}` | ชื่อ field ซ้ำ parser บางแบบอาจยุบเหลือค่าหลัง ต้องตรวจไม่ให้หลุดผ่าน |
| `{"answer":"<think>...</think>2"}` | มี Thinking marker ปะปน |

คำว่า **case-sensitive** แปลว่าสนใจตัวพิมพ์เล็ก/ใหญ่ เช่น `answer` กับ `Answer` ไม่ถือว่าเป็นชื่อเดียวกันตาม contract นี้

นอกจากนี้ยังต้องตรวจชั้นนอกว่า model ตรง, `done` เป็น boolean true และ `done_reason` เป็น `stop` การ validate โครงสร้างไม่ได้รับรองว่าเนื้อหา เช่น ชื่อเมืองหลวงหรือผลลบเลข จะถูกจริง

## 6. อ่านค่าที่ส่งให้โมเดลทีละตัว

ค่าต่อไปนี้ใช้กับ contract/smoke test ของ AI-002 ส่วน interactive chat มีค่าต่างกันตามที่ระบุท้ายหัวข้อนี้

| Field/ศัพท์ | ความหมาย | ทำไมเราใช้ |
| --- | --- | --- |
| `model` | เลือกโมเดล | ยืนยันว่าเป็น `qwen3:4b` ตามโจทย์ ไม่เผลอทดสอบรุ่นอื่น |
| `prompt` | คำถามหรือคำสั่งของผู้ใช้ | นำข้อความที่ต้องการทดสอบให้โมเดลตอบ |
| `system` / system prompt | คำสั่งกำกับวิธีตอบ เช่น ภาษา ความกระชับ และรูปแบบ | ให้ตอบสั้น ภาษาเดียวกับผู้ใช้ และเก็บคำตอบสุดท้ายใน answer |
| `stream=false` | ขอผลรวมชุดเดียวเมื่อจบ แทนส่งทีละช่วง | ตรวจ JSON และ completion จากผลสุดท้ายได้ตรงไปตรงมา |
| `think=false` | ขอไม่เปิด thinking ตามความสามารถของ runtime/model | ยังต้องตรวจผลจริง เพราะ flag อย่างเดียวไม่รับประกันข้ามรุ่น |
| `format` | schema ของคำตอบที่ต้องการ | ขอ object ที่มี answer string ช่องเดียว |
| `temperature=0` | ลดความสุ่มของการเลือก token | ลดความแปรปรวน แต่ไม่รับประกันคำตอบเดิมทุกครั้งหรือความถูกต้อง |
| `num_predict=256` | เพดานจำนวน token ที่ให้ generate | จำกัดความยาวและต้องตรวจว่าคำตอบไม่ถูกตัด |

**Token — โทเคน** คือหน่วยข้อความที่โมเดลประมวลผล หนึ่ง token ไม่จำเป็นต้องเท่ากับหนึ่งคำหรือหนึ่งตัวอักษร โดยเฉพาะเมื่อเปลี่ยนภาษา จึงห้ามบอกว่า `256` แปลว่า 256 คำไทยแน่นอน

**Thinking marker** คือข้อความเครื่องหมายอย่าง `<think>` และ `</think>` ที่อาจใช้ครอบส่วนคิด เราไม่ต้องการให้หลุดเป็นคำตอบผู้ใช้ การตรวจว่าไม่มี marker ไม่ได้พิสูจน์ว่าโมเดลไม่มีการประมวลผลภายใน และข้อความที่ไม่มี marker ก็อาจตอบผิดหรือไม่ตรงคำถามได้

**Prompt injection** ในชุดทดสอบคือข้อความที่พยายามเปลี่ยนวิธีตอบ เช่น สั่งให้แสดง `<think>` หรือไม่ทำตามรูปแบบเดิม เราทดสอบเพื่อดูการหลงคำสั่งและการรั่วของรูปแบบ ไม่ได้อ้างว่าชุดเล็กนี้พิสูจน์ความปลอดภัยทุกวิธีโจมตี

**Truncated response — คำตอบถูกตัด** เช่นชนเพดานแล้วได้ `done_reason=length` ห้ามรับเป็นคำตอบครบ แม้ข้อความบางส่วนดูอ่านรู้เรื่อง ส่วน `done=true` อย่างเดียวก็ยังไม่พอ ต้องตรวจ reason และข้อมูลอื่นร่วมกัน

`done=true` หมายถึง Ollama รายงานว่าจบการ generate แล้ว ส่วน `done_reason=stop` เป็นเหตุจบตามปกติที่ contract นี้ยอมรับ ต่างจาก `length` ที่จบเพราะชนเพดาน ทั้งสอง field ไม่ได้ใช้รับรองว่าคำตอบถูกข้อเท็จจริง

**Stateless** หมายถึงไม่ส่งประวัติคำถามก่อนหน้าไปด้วย `chat-ollama.ps1` ของเราเป็นตัวช่วยถามทีละข้อความ จึงอย่าคาดหวังว่าจะจำบทสนทนาก่อนหน้าโดยอัตโนมัติ

interactive helper ใช้ `temperature=0.2`, `num_predict=512` และ system prompt ของตัวเอง ส่วน AI-003 ใช้เส้นทาง Backend ตาม contract จึงไม่ควรใช้ความเร็วหรือคำตอบจาก helper แทนผล E2E

## 7. AI-001 ทำอะไร และแต่ละการตรวจพิสูจน์แค่ไหน

**CLI — Command Line Interface** คือการใช้คำสั่งใน terminal เช่น `ollama list` และ `ollama run qwen3:4b` ส่วน **terminal** คือหน้าต่างรับคำสั่ง และ **PowerShell** คือโปรแกรมที่ตีความคำสั่งภายในหน้าต่างนั้น

| ตรวจอะไร | พิสูจน์อะไร | ยังไม่ได้พิสูจน์อะไร |
| --- | --- | --- |
| `ollama --version` | เรียกโปรแกรม Ollama ได้และรู้เวอร์ชัน | โมเดลสร้างคำตอบได้หรือไม่ |
| `ollama list` | มีรายการโมเดลที่ดาวน์โหลดไว้ | โมเดลกำลังโหลดอยู่ใน RAM/VRAM หรือยัง |
| `ollama ps` | ดูโมเดลที่ runtime กำลังโหลด/รัน | ความถูกต้องของทุกคำตอบ |
| `ollama run qwen3:4b` แล้วถาม | CLI เรียกโมเดลและได้ข้อความตอบจริง | Backend เชื่อมต่อถูกหรือไม่ |
| `GET /api/version` | HTTP endpoint ของ Ollama ตอบได้ | structured generation ผ่าน contract หรือไม่ |
| `test-ollama.ps1` ผ่าน | request จริงและ response ผ่าน checks ของ smoke script | คำตอบความรู้ทุกเรื่องถูกหรือไม่ |
| เรียก unused endpoint แล้ว fail ตามคาด | เครื่องมือรายงานปลายทางไม่พร้อมได้ | ไม่ได้แปลว่าได้ปิด/ทดสอบทุก failure mode ของ Ollama จริง |

**Smoke test — สโมกเทสต์** คือการทดสอบพื้นฐานเพื่อเช็กว่าเส้นทางหลักทำงาน เช่น ส่งหนึ่งคำถามแล้วตรวจผล ไม่ใช่การรับรองระบบครบทุกกรณี

คู่มือ AI-001 เพิ่มวิธีเริ่มจากศูนย์ เปิด PowerShell, ติดตั้ง Ollama/โมเดล/Git/PowerShell 7, ดึง Repository และแก้ปัญหาที่พบจริง เช่นไม่มี `irm`, ไม่มี `pwsh` หรือ Desktop อยู่คนละ path

เพื่อนทดลองบนเครื่องใหม่แล้วผ่านการติดตั้ง runtime/โมเดล, CLI, manual REST API, บันทึก JSON และ endpoint ไม่พร้อม ส่วน clone และสคริปต์ Repository บนเครื่องเพื่อนยังไม่ได้ยืนยัน เพราะติดสิทธิ์ Repository และตอนตรวจยังไม่พบ `pwsh` จึงไม่ควรบอกว่า “เพื่อนทำทุกขั้นตอนครบแล้ว”

## 8. AI-002 ทำ Contract และแยกความล้มเหลวอย่างไร

**Integration — อินทิเกรชัน** คือการเชื่อมส่วนต่าง ๆ ให้ทำงานร่วมกัน **Contract — คอนแทร็กต์** คือข้อตกลงร่วมกันว่าต้องส่งข้อมูลอะไร รับข้อมูลแบบไหน ตรวจอย่างไร และเมื่อผิดให้จำแนกเป็นอะไร

Contract ช่วยให้ Backend Developer เขียนการเชื่อมต่อโดยไม่ต้องเดาว่าจะได้ field อะไร ห้ามนำ partial output มาแสดงเหมือนเป็นผลสำเร็จเพียงเพราะ request ไม่ throw error

| ประเภท | ตัวอย่าง | วิธีอธิบาย |
| --- | --- | --- |
| Provider unavailable | ติดต่อ Ollama ไม่ได้ | บริการปลายทางยังเรียกไม่ได้ |
| Provider timeout | เกินเวลาที่กำหนดแล้วยังไม่ได้ผลครบ | บริการตอบไม่ทันเวลาที่เรายอมรอ |
| Request cancelled | ผู้ใช้กดยกเลิกหรือปิดการเชื่อมต่อ | ผู้ใช้/คำขอหยุดรอ ไม่ใช่สรุปว่า provider ช้า |
| Provider error | Ollama ตอบ HTTP status ไม่ตรง success ที่ตกลง | ได้ response แต่สถานะไม่ใช่ HTTP 200 ตาม contract |
| Invalid/incomplete response | done=false, JSON ผิด, model ผิด, answer ว่าง | ข้อมูลไม่ผ่านกติกา จึงห้ามแสดงเป็น success |
| Truncated response | done_reason=length | คำตอบไม่จบตามที่ contract ต้องการ |

**Timeout** เป็นขีดจำกัดเวลารอ ไม่ใช่เวลาที่โมเดลต้องใช้จริงเสมอ และไม่ใช่ timeout แล้วรู้ผลสุดท้ายว่าโมเดลจะตอบอะไร

**Cancellation token** เป็นกลไกในโค้ด .NET ที่ส่งสัญญาณให้ส่วนต่าง ๆ รู้ว่ามีการยกเลิก ควรแยกต้นทางการยกเลิกออกจาก timeout มิฉะนั้นอาจรายงานสาเหตุผิด

**Preflight** ใน smoke script คือการตรวจเบื้องต้นด้วย `/api/version` ก่อนส่งคำถามจริง ไม่ใช่การตรวจความพร้อมครบทุกด้าน และไม่ใช่คำว่า CORS preflight ใน browser

**Redirect** คือ HTTP บอกให้ไป URL อื่น สคริปต์ของเราปิดการตาม redirect เพื่อไม่ให้เริ่มจาก loopback แล้วถูกส่งต่อไปปลายทางอื่น **Proxy** คือบริการคั่นกลางที่ส่งคำขอแทนเรา helper ใช้ NoProxy เพื่อให้คำขอ local ไม่ผ่าน proxy

## 9. AI-003 ตรวจอะไร และทำไม 200 ยังตกได้

**End-to-End / E2E — เอนด์ทูเอนด์** ใน Issue นี้หมายถึงส่งผ่าน Backend แล้วถึง Ollama/โมเดลและรับคำตอบกลับมาตรวจทั้งเส้นทาง ไม่รวมการกดหน้าเว็บ เพราะขอบเขตนี้ตรวจ HTTP API

**Dataset** คือชุดข้อมูลทดสอบ ของเรามี 160 cases หมวดละ 40 **Test case** คือหนึ่งกรณี มี ID, หมวด, ภาษา, คำถามและเกณฑ์คำตอบ เช่น `math-39` ใช้อ้างอิงข้อเดิมได้แม้เอกสารเรียงใหม่

**Edge case — เอดจ์เคส** คือกรณีที่ไม่ใช่ข้อความถามเรียบ ๆ เช่น Emoji, newline, รูปแบบพิเศษ และข้อความล่อให้แสดง thinking ใช้ดูว่าส่วนที่ต่างจากปกติทำให้ระบบพังหรือหลุดกติกาหรือไม่

**Evaluator — อีแวลูเอเตอร์** คือโปรแกรมตรวจผล ในงานนี้ `test-chat-e2e.ps1` ส่งแต่ละคำถาม ตรวจ response และบันทึกเหตุผลผ่าน/ไม่ผ่าน

ทุกข้อจะผ่านเมื่อ HTTP 200, model ตรง, response เป็น string ไม่ว่าง, ไม่มี JSON ซ้อน/Thinking marker/รูปแบบรายละเอียดระบบที่ตรวจ, ภาษาตรงตามเกณฑ์ และคำตอบแน่นอนตรง expected answer

**Expected answer** คือคำตอบที่ใช้เป็นเกณฑ์ **Regex — regular expression** คือรูปแบบข้อความที่ใช้ตรวจว่าคำตอบตรงสิ่งที่ยอมรับได้หรือไม่ เช่น ยอมรับคำว่า `ดวงอาทิตย์` หรือ `อาทิตย์` ตามคำถาม

Regex ไม่ใช่ AI ที่เข้าใจทุกความหมาย หากกฎแคบเกินจะตัดคำตอบถูก หากกว้างเกินก็อาจรับประโยคผิดที่มีคำสำคัญติดอยู่ จึงต้องตรวจเกณฑ์และอ่านคำตอบจริงประกอบ ไม่ใช้ regex แทน JSON parser และไม่อ้างว่าตรวจข้อเท็จจริงได้ทุกเรื่อง

**False negative** คือระบบตรวจบอกว่าไม่ผ่านทั้งที่คำตอบควรผ่าน ตัวอย่างรอบแรกไม่ยอมรับคำพ้อง `อาทิตย์` และ `Honeybees` จึงแก้เกณฑ์ให้รับคำตอบที่ถูก แล้วรันจริงใหม่ครบชุด **False positive** คือระบบบอกผ่านทั้งที่ควรตก เช่นรับ `17 วัน` เพราะมองเห็นเพียงเลข `7`

**Oracle** ในการทดสอบคือวิธีอ้างอิงคำตอบที่ถูก สำหรับเลขคำนวณเราใช้การคำนวณแยกจากโมเดลเพื่อตรวจ expected answers ไม่ใช้คำตอบโมเดลเป็นผู้ตรวจตัวเอง

ผลจริงฉบับสุดท้าย:

| หมวด | ผ่าน | ไม่ผ่าน |
| --- | ---: | ---: |
| ไทย 40 ข้อ | 30 | 10 |
| อังกฤษ 40 ข้อ | 38 | 2 |
| คำนวณ 40 ข้อ | 39 | 1 |
| Edge 40 ข้อ | 34 | 6 |
| **รวม 160 ข้อ** | **141** | **19** |

HTTP 200 มี 157 ข้อ แต่ผ่านคุณภาพ 141 ข้อ จึงมี 16 ข้อที่ส่งสำเร็จแต่ยังไม่ผ่านคุณภาพ อีก 3 ข้อเป็น HTTP 502 `AI_INVALID_RESPONSE` รวมตก 19 ข้อ

เช่น `1 - 9` ตอบ `0` เป็นปัญหาความถูกต้อง ส่วนคำถามที่ขอหน่วย Celsius แล้วตอบแค่ตัวเลขถูก เป็นปัญหาไม่ทำตามรูปแบบ/หน่วย ไม่ควรรายงานว่าเลขคำนวณผิดทั้งสองแบบ

502 ทั้งสามข้อยังไม่มีหลักฐานสาเหตุย่อยจาก public response พอให้ฟันธงว่า token หมด อย่าอธิบายสาเหตุแทนฝ่าย Backend โดยไม่มีข้อมูลเพิ่ม

## 10. อ่านผลทดสอบอัตโนมัติและหลักฐาน

**Mock — ม็อก** คือปลายทางจำลองที่เราควบคุมให้ตอบแบบที่ต้องการ เช่นหน่วงจน timeout หรือคืน JSON ผิด เพื่อดูว่าสคริปต์ปฏิเสธได้จริง **Live test** คือเรียกบริการ/โมเดลจริง

Mock ผ่านพิสูจน์ว่าเครื่องมือตรวจทำงานตามกรณีที่ทดสอบ ไม่ได้พิสูจน์ว่าโมเดลตอบทุกคำถามถูก Live test จึงยังจำเป็นสำหรับคุณภาพคำตอบ

**Unit test** มักตรวจพฤติกรรมส่วนเล็กที่แยกได้ **Integration test** ตรวจส่วนที่ทำงานร่วมกัน **Regression test** คือการตรวจป้องกันสิ่งที่เคยทำงานแล้วเสียหลังแก้ คำเหล่านี้อธิบายคนละมุม การทดสอบหนึ่งชุดอาจเป็นทั้ง integration และ regression ได้

**Test method** คือหนึ่งฟังก์ชันทดสอบ ส่วน **scenario/subtest** คือหลายรูปแบบข้อมูลที่ฟังก์ชันนั้นลอง ดังนั้น 26 test methods ไม่ได้แปลว่าตรวจเพียง 26 คำถาม และไม่ใช่เลขเดียวกับ dataset 160 ข้อ

รอบทบทวนที่บันทึกในคู่มือหลัก: Python ผ่าน 26 methods, Backend ผ่าน 135 tests และ live smoke หลังแก้ helper ตอบ `2` ผ่าน ขณะที่ผล E2E เดิมยังเป็น 141/160 เพราะไม่ได้แก้ Backend/dataset/evaluator หรือรันชุดนั้นใหม่ในรอบแก้ helper

**Exit code** คือเลขที่โปรแกรมคืนให้ผู้เรียกเมื่อจบ สำหรับ smoke/evaluator ของเรา `0` แปลว่าผ่านเงื่อนไขทั้งหมด `1` แปลว่ามี failure การที่ evaluator คืน 1 เมื่อมี 19 ข้อตกคือการทำงานถูกของเครื่องมือตรวจ ไม่จำเป็นต้องแปลว่าตัวสคริปต์เขียนพัง

interactive chat ต่างออกไป: จับ error ของแต่ละคำถาม แสดงข้อความ และให้ถามต่อได้ ไม่ได้จบโปรแกรมทันทีทุกครั้งที่ provider ผิด ส่วน launcher ต้องส่ง exit code ของโปรแกรมลูกกลับอย่างถูกต้อง

**Evidence — หลักฐาน** เก็บสิ่งที่เกิดจริง เช่น request, raw response, HTTP status, case ID, เวลา และเหตุผล **Raw response** คือเนื้อหาที่รับมาจริงก่อนย่อเป็นรายงาน ช่วยให้คนอื่นตรวจซ้ำได้

**Reproduce — รีโพรดิวซ์** คือทำตามเงื่อนไขเดิมเพื่อให้ตรวจเหตุการณ์ซ้ำได้ จึงต้องมีวิธีรัน รุ่นซอฟต์แวร์ hardware และชุดข้อมูล ไม่ใช่มีแต่คำว่า PASS

**SHA-256/hash** เป็นค่าลายนิ้วมือจากเนื้อหาไฟล์ ใช้เชื่อมว่าหลักฐานใช้ dataset/evaluator รุ่นไหน Hash ตรงไม่ได้แปลว่าคำตอบถูกหรือไม่มี secret ทุกชนิด

**Atomic write** ใน smoke helper คือเขียนไฟล์ชั่วคราวให้ครบก่อนแทนไฟล์หลัก เพื่อลดโอกาสทำหลักฐานเก่าเสียเมื่อเขียนไม่ครบ ถ้าคำขอใหม่ fail แล้วไฟล์เก่ายังอยู่ ต้องดู exit code และ timestamp ไม่เข้าใจว่าไฟล์นั้นเป็นผลสำเร็จของรอบใหม่

**Secret** คือข้อมูลลับ เช่น password, access token หรือ API key **ข้อมูลส่วนตัว** เช่นชื่อบัญชีจริง ชื่อเครื่องหรือข้อมูลระบุตัวบุคคลที่ไม่จำเป็น หลักฐานต้องไม่เก็บสิ่งเหล่านี้ การค้น credential pattern เป็นการช่วยตรวจ ไม่ใช่หลักฐานรับรองว่าไม่มีข้อมูลลับทุกแบบแน่นอน

## 11. Cold, Warm, Latency, Average และ p95

**Latency — เลเทนซี** คือเวลาที่รอจนได้ผล ใน AI-003 สคริปต์จับเวลาฝั่งผู้เรียกตั้งแต่ก่อนสร้าง payload ผ่านส่ง request อ่าน response และตรวจผล จึงรวมเวลาประมวลผลของ Backend/Ollama และ overhead การตรวจ ไม่ใช่เวลาที่โมเดล generate ล้วน ๆ และไม่ใช่ token ต่อวินาที

**Cold Start** ในรายงานนี้คือคำถามแรกหลังสั่ง unload โมเดลและยืนยันว่าไม่ได้โหลดอยู่ Backend เปิดไว้แล้ว จึงวัดผลการเริ่มโหลดโมเดล ไม่ใช่เวลาตั้งแต่เปิดคอมพิวเตอร์ **Warm Request** คือคำขอถัดมาขณะโมเดลยังพร้อมใช้งาน

แค่ “คำถามแรกของสคริปต์” ยังไม่พอจะยืนยัน cold เพราะโมเดลอาจโหลดจากการใช้งานก่อนแล้ว ถ้าไม่ควบคุมสถานะให้เรียก first request/cold candidate ตามหลักฐาน

| ตัวเลขจริง | อ่านอย่างไร |
| --- | --- |
| Cold 4,953 ms | 4.953 วินาที ของคำขอแรกหลัง unload โมเดลตามขั้นตอนที่บันทึก |
| Warm ทั้งหมด 159 ข้อ เฉลี่ย 383.2 ms | รวมทั้งข้อที่ผ่านและไม่ผ่านคุณภาพ |
| Warm ที่ผ่าน 140 ข้อ เฉลี่ย 284.1 ms | นับเฉพาะข้อที่ผ่านทุกเกณฑ์ ต้องบอกตัวหารให้ชัด |
| Warm ที่ผ่าน median 253 ms | ค่ากลางเมื่อเรียงเวลา ไม่ใช่ค่าเฉลี่ย |
| Warm ทั้งหมด p95 631 ms | ตาม nearest rank ประมาณ 95% ของ warm ที่วัดมีเวลาไม่เกินจุดนี้ |

**Average/mean** คือผลรวมเวลาหารจำนวนคำขอ ส่วน **median** คือค่ากลางของเวลาที่เรียงแล้ว ช่วยไม่ให้ค่าช้าผิดปกติมีผลเหมือนค่าเฉลี่ย **p95** คำนวณโดยเรียงเวลาแล้วเลือกอันดับ `ceil(0.95 × จำนวนตัวอย่าง)` ตามวิธี nearest rank ไม่ใช่อัตราตอบถูก 95% และไม่ใช่เวลาสูงสุด

หน่วย `ms` คือมิลลิวินาที โดย 1,000 ms = 1 วินาที เวลาเหล่านี้มาจากเครื่องเดียว ส่งทีละคำขอ ไม่ใช่ **load test** ที่ให้ผู้ใช้จำนวนมากเรียกพร้อมกัน และไม่ใช่การรับประกันเวลาเครื่องอื่น

Live smoke ใหม่ของ Ollama helper วัด 10,019 ms แต่ไม่ได้ควบคุม unload ก่อน จึงเรียกตัวเลขนั้นว่า confirmed cold ไม่ได้ และเป็น Ollama ตรง ไม่ใช่ผล AI-003 รอบใหม่

## 12. เครื่องมือและสัญลักษณ์คำสั่งที่เคยทำให้สับสน

| คำ/สัญลักษณ์ | ความหมายและตัวอย่าง |
| --- | --- |
| Windows PowerShell / `powershell.exe` | โปรแกรม PowerShell ที่มีมากับ Windows บางรุ่น เครื่องที่พบในงานเป็น 5.1 |
| PowerShell 7 / `pwsh.exe` | โปรแกรมอีกเวอร์ชันที่ต้องติดตั้งหรือมี runtime พร้อม สคริปต์ AI รุ่นปัจจุบันกำหนด version 7 ขึ้นไป |
| PATH | รายการโฟลเดอร์ที่ระบบใช้ค้นหาโปรแกรมเมื่อพิมพ์ชื่อ เช่น pwsh ไม่พบอาจยังไม่ติดตั้งหรือยังค้นไม่เจอ ไม่ได้แปลว่า Ollama เสีย |
| `irm` | alias หรือชื่อย่อของ `Invoke-RestMethod` ถ้าใช้ผิด shell หรือ environment ไม่มี alias อาจไม่รู้จัก ใช้ชื่อเต็มใน PowerShell ตามคู่มือ |
| `Invoke-RestMethod` | คำสั่งส่ง HTTP และอ่านข้อมูลตอบกลับในรูปที่ใช้งานได้ |
| `Invoke-WebRequest` | ส่ง HTTP และให้เข้าถึง status/body เพื่อ validate แบบที่ helper ใช้ |
| `$body` / `$response` | ชื่อตัวแปร PowerShell ต้องมี `$` ด้านหน้า `body = ...` จะถูกตีความต่างและอาจกลายเป็นเรียกคำสั่งที่ไม่มี |
| `@{ ... }` | สร้าง hashtable หรือชุด key/value ใน PowerShell ยังไม่ใช่ข้อความ JSON จนกว่าจะ ConvertTo-Json |
| `$false` | ค่า boolean false ของ PowerShell ส่วน JSON เขียน `false` โดยไม่มี `$` |
| `|` | pipe ส่งผลจากคำสั่งซ้ายไปให้คำสั่งขวา เช่นแปลง response เป็น JSON แล้วบันทึกไฟล์ |
| `PS C:\...>` | prompt บอกว่า PowerShell รอคำสั่ง ไม่ใช่ช่องถามโมเดล ห้ามคัดส่วน PS/path นี้ไปรวมกับคำสั่ง |
| `>>` | PowerShell มักกำลังรอคำสั่งหลายบรรทัดให้ครบ ถ้าเปิดวงเล็บ/quote ค้าง ให้ตรวจคำสั่งหรือ Ctrl+C แล้วย้อนเริ่ม block ใหม่ |
| `คุณ:` | prompt ของ interactive chat เมื่อเห็นแล้วจึงพิมพ์คำถามเพื่อส่งให้โมเดล |
| `.\scripts\...` | path แบบ relative อ้างจากโฟลเดอร์ปัจจุบัน ถ้าอยู่ผิดโฟลเดอร์จะหา script ไม่เจอ |
| `$HOME` | โฟลเดอร์ผู้ใช้ ไม่ได้แปลว่ามี Desktop ย่อยเสมอ บางเครื่องย้าย Desktop ไป OneDrive |
| `$LASTEXITCODE` | อ่านรหัสออกของโปรแกรมภายนอกล่าสุด ควรตรวจทันทีหลังรันตัวที่ต้องการตรวจ |

ตัวอย่างนี้เป็น **คำสั่งเปิดตัวแชท** ไม่ใช่คำถามที่ส่งให้โมเดล:

```powershell
pwsh -NoProfile -File .\scripts\chat-ollama.ps1
```

`-NoProfile` หมายถึงไม่โหลดไฟล์ตั้งค่าส่วนตัวของ PowerShell และ `-File` ระบุสคริปต์ที่จะรัน หลังสคริปต์เปิดและเห็น `คุณ:` ค่อยพิมพ์เช่น “ช่วยอธิบาย API แบบง่าย ๆ” ใช้ `/bye` ออกจากตัวแชท

**Python** ใช้รัน unittest ที่เราสร้าง ไม่ได้เป็น runtime ของ Qwen **`py -3`** คือเรียก Python 3 ผ่าน Python Launcher บน Windows ไม่ใช่การติดตั้ง Python ให้อัตโนมัติ

**.NET SDK** คือชุดเครื่องมือ build/run/test โปรแกรม .NET ส่วน **ASP.NET Core** เป็น framework ของ Backend นี้ `dotnet test` ทดสอบโค้ด .NET ของทีม ไม่ได้แปลว่าจะส่งคำถามจริงครบ 160 ข้อให้โมเดลแทน evaluator

### Hardware ที่รายงานหมายถึงอะไร

**RAM** คือหน่วยความจำหลักของเครื่อง **GPU** คือหน่วยประมวลผลกราฟิกที่ช่วยงานคำนวณโมเดลได้ **VRAM** คือหน่วยความจำของ GPU ส่วน disk เป็นที่เก็บไฟล์โมเดลระยะยาว การมีไฟล์โมเดลอยู่บน disk ไม่เท่ากับโหลดเข้า RAM/VRAM แล้ว

เครื่องทดสอบหลักใช้ RAM ระดับ 16 GB และ RTX 4050 Laptop VRAM 6141 MiB, Ollama 0.40.5 ข้อมูลนี้ใช้บอกบริบทผล ไม่ได้พิสูจน์ว่า hardware อื่นจะมีเวลาเท่ากัน Reviewer ยอมรับ RTX 4050 สำหรับ AI-002 แล้วตามที่บันทึก แต่ไม่ขยายเป็นคำรับรองทุกงานโดยอัตโนมัติ

คำว่า Backend รันใน environment ชื่อ `Production` ในรายงานหมายถึงโหมด configuration ของแอปที่ทดสอบในเครื่อง ไม่ได้แปลว่า deploy ขึ้น production server หรือเปิด public แล้ว

| main | ชื่อ branch หลักของทีม | ไม่ใช่ชื่อเรียกทุกไฟล์หรือทุก branch |
| commit | บันทึกชุดการเปลี่ยนแปลงไว้ในประวัติ | commit ในเครื่องยังไม่ได้ upload เอง |
| fetch | รับประวัติและข้อมูล remote ล่าสุด | ยังไม่รวมเข้า branch ที่กำลังทำอัตโนมัติ |
| pull | รับข้อมูลแล้วรวมตามวิธีที่ Git ตั้งค่า | เปลี่ยนไฟล์/ประวัติ local ได้ ต้องรู้ branch และสถานะก่อน |
| push | ส่ง commits/branch ไป remote | เป็นการ upload ต้องเป็นไปตามคำอนุญาต |
| Pull Request / PR | ขอให้ทีมตรวจและพิจารณารวม branch | การสร้าง PR ยังไม่ใช่การ merge |
| review | อ่าน ตรวจผล และให้ข้อเสนอแนะ/อนุมัติ | ทดสอบผ่านไม่ได้แทนการอนุมัติของคน |
| merge | รวมประวัติงานเข้า branch ปลายทาง | merge เข้า main ต้องมีสิทธิ์และการอนุญาตตามทีม |
| diff | ส่วนต่างว่าเพิ่ม ลบ หรือแก้อะไร | ใช้ตรวจงานก่อน commit/review |

**Acceptance Criteria** คือเกณฑ์ที่งานต้องผ่าน **Deliverables** คือสิ่งที่ต้องส่ง เช่นเอกสาร/สคริปต์/หลักฐาน **Definition of Done** คือเงื่อนไขปิดงานทั้งกระบวนการ ซึ่งอาจรวม review และ merge ด้วย

ดังนั้น “สร้างสคริปต์แล้ว”, “ทดสอบครบแล้ว”, “ทุกข้อผ่านแล้ว”, “สร้าง PR แล้ว” และ “merge แล้ว” ไม่ใช่สถานะเดียวกัน AI-003 ทำชุดทดสอบและหลักฐานครบ แต่คุณภาพในผลหลักยังมี 19 failure ส่วนสถานะ push/PR/review/merge ต้องตรวจจาก GitHub ล่าสุด

## 14. ซ้อมอธิบายโดยไม่ต้องจำศัพท์ทั้งหมด

**ถ้าพี่ถาม “ทำอะไรไปบ้าง?”**

> ผมแยกทำสามขั้นครับ 001 เตรียมเครื่องและคู่มือให้เรียกโมเดลได้ 002 กำหนดรูปแบบข้อมูลกับวิธีตรวจให้ Backend เชื่อมต่อ และ 003 ส่งคำถามผ่าน Backend จริง 160 ข้อเพื่อดูทั้งรูปแบบ ภาษา เนื้อหาและเวลา ไม่ได้สร้างหน้าเว็บหรือแก้ Backend ในงานประเมินนี้ครับ

**ถ้าพี่ถาม “ทำไมต้อง structured output?”**

> เพื่อให้โปรแกรมรู้ว่าคำตอบอยู่ field ไหนและตรวจชนิดได้ครับ เช่นให้มี answer เป็น string ช่องเดียว แต่ยังต้องตรวจเนื้อหาต่างหาก เพราะ JSON ที่ถูกอาจตอบเลขหรือข้อเท็จจริงผิดได้

**ถ้าพี่ถาม “ทำไม parse สองชั้น?”**

> Ollama ส่ง JSON ชั้นนอก และ field response ข้างในยังเป็นข้อความ JSON ครับ ต้องอ่านชั้นนอกก่อน แล้ว parse string นั้นอีกครั้งจึงอ่าน answer จากนั้น Backend ค่อยส่งข้อความล้วนใน response ให้ผู้เรียก

**ถ้าพี่ถาม “ตอนนี้ผ่านหมดหรือยัง?”**

> ยังครับ E2E ผ่าน 141 จาก 160 ข้อ ตก 19 มี HTTP 502 สามข้อและคำตอบที่ส่งสำเร็จแต่คุณภาพไม่ผ่านอีก 16 ข้อ ผมเก็บคำถาม คำตอบจริง เวลา และเหตุผลครบไว้แล้ว ไม่ปรับผลให้ดูผ่านครับ

**ถ้าพี่ถาม “แก้ยังไงต่อ?”**

> ขอให้ทีมแยกประเภท failure และมอบหมายคนรับผิดชอบก่อนครับ งานรูปแบบ/provider เป็นฝั่ง Backend หรือ contract ส่วนคำตอบผิด/ทำตามคำสั่งเป็นงานคุณภาพ prompt/model ตามขอบเขตที่อนุมัติ หลังแก้จึงใช้ dataset เดิมตรวจ regression และเปรียบเทียบผล ไม่เปลี่ยน model หรือ controller เองใน AI-003

**ถ้าพี่ถาม “เร็วแค่ไหน?”**

> เครื่องนี้คำขอแรกหลัง unload โมเดลใช้ 4.953 วินาทีครับ warm ทั้ง 159 คำขอเฉลี่ย 383.2 มิลลิวินาที เป็นเวลาที่สคริปต์เห็นรวม Backend และการตรวจผล ส่งทีละคำขอ ไม่ใช่ผลหลายผู้ใช้หรือการรับประกัน production

**ถ้าพี่ถามสิ่งที่ยังไม่ได้ทดสอบ** ให้ตอบว่า “ส่วนนี้ยังไม่มีหลักฐานยืนยันครับ” แล้วระบุสิ่งที่จะต้องตรวจเพิ่ม แยกสิ่งที่เห็นจริงออกจากสาเหตุที่คาดไว้ ไม่จำเป็นต้องเดาคำตอบให้ครบทุกเรื่อง
