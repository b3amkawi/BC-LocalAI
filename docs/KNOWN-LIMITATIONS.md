# ข้อจำกัดที่ทราบ (Known Limitations) — BE-002 Ollama Integration

เอกสารนี้สรุปข้อจำกัดของ `/api/chat` ที่เชื่อมกับ Ollama (`qwen3:4b`) เพื่อให้ผู้รีวิวตัดสินใจก่อน merge
แต่ละข้อระบุว่า **วัดจริง** หรือ **ประมาณการ** อย่างชัดเจน

**สเปกอ้างอิงของโปรเจกต์:** ASUS TUF Gaming F16, Intel Core 5 210H, RAM 16 GB, NVIDIA RTX 4050 Laptop GPU (VRAM 6 GB)

ตัวเลขในเอกสารนี้วัดวันที่ 2026-10-19/20 บนเครื่องที่แรงกว่าสเปกอ้างอิง: Acer Predator PHN16-72, Intel Core i7-14700HX, RAM 16 GB, NVIDIA RTX 4060 Laptop GPU (VRAM 8 GB), Windows 11, Ollama กับ `qwen3:4b`
เครื่องนี้สร้างคำตอบได้ 73–77 token/วินาที ส่วนสเปกอ้างอิงได้ราว 60 token/วินาที (ผล AI-004) **บนสเปกอ้างอิงให้คาดว่าเวลาจะนานขึ้นราว 25%** ส่วนผลผ่าน/ไม่ผ่านและ error code ไม่ขึ้นกับ GPU

## 1. คำตอบยาวเกินเพดาน output token ได้ 502 `AI_RESPONSE_TOO_LARGE` (วัดจริง, แก้โดย BE-003)

**ก่อน BE-003:** เพดานคือ `num_predict = 256` ตายตัวในโค้ด ติดขอบความยาวคำตอบจริง (คำตอบที่ยาวที่สุดที่วัดได้ใช้ 247 - 279 token) จึงมีคำถามจำนวนหนึ่งถูก
Ollama ตัด (`done_reason = "length"`) แล้วได้ `AI_INVALID_RESPONSE` ซึ่งแยกไม่ออกจาก response เสียจริง (คำถามเรื่องประวัติศาสตร์ล้ม 6 จาก 6 ครั้ง)

**หลัง BE-003:**
- เพดานเป็นค่าตั้ง `Ollama:MaxOutputTokens` ค่าเริ่มต้น **1024** (ช่วง 16 - 4096) คำถามเดิมสำเร็จ 6 จาก 6 ครั้ง (ใช้ 177 - 279 token)
- ถ้าคำตอบยังเกินเพดาน จะได้ **502 `AI_RESPONSE_TOO_LARGE`** (รหัสใหม่ แยกจาก `AI_INVALID_RESPONSE`) และหน้าเว็บแสดง
  "คำตอบยาวเกินกว่าที่ระบบรองรับ กรุณาถามให้สั้นลงหรือแบ่งเป็นหลายคำถาม" (วัดจริงด้วยการตั้งเพดาน 32)
- มีเพดานขนาด response body (`Ollama:MaxResponseBytes` ค่าเริ่มต้น 1 MiB) อ่านทีละส่วนและหยุดทันทีที่เกิน
- ต้นทุน: คำตอบที่ใช้เพดานเต็ม 1024 token ใช้เวลาราว 13 วินาที (77 token/วินาที) เทียบกับราว 3.3 วินาทีที่ 256 token ใน worst case คิวใน Ollama จึงยาวขึ้น
- รายละเอียดและหลักฐาน: [BE-003-ROOT-CAUSE.md](BE-003-ROOT-CAUSE.md), [BE-003-CONFIGURATION.md](BE-003-CONFIGURATION.md), [BE-003-VERIFICATION.md](BE-003-VERIFICATION.md)
- ข้อจำกัดที่ยังเหลือ: AI-002 (`docs/ai/ollama-integration-contract.md`) ยังระบุ `num_predict = 256` ผู้ดูแลฝั่ง AI ควรปรับเอกสารให้ตรง

## 2. Ollama ประมวลผลทีละคำขอ (วัดจริง + ประมาณการ)

วัดซ้ำหลัง BE-003 (ค่าเริ่มต้นใหม่): ผลเท่าเดิม ไม่มีการเพิ่มตัวจำกัดจำนวนคำขอพร้อมกัน (10 คำขอ 3 ประโยค รวม 24.3 วินาที, โหลดเกินได้ 4 x 200 + 11 x 504 แล้วกลับมาปกติทันที) นโยบาย timeout/concurrency สุดท้ายต้องรอผล AI-004

ผล benchmark ของ AI-004 (`docs/performance/benchmark-report.md`) ยืนยันตรงกัน: throughput คงที่เมื่อยิงพร้อมกัน 1 หรือ 10 ตัว มีแต่เวลารอคิวที่เพิ่ม และไม่เคยเกิด timeout เลย (นานสุด 28.7 วินาที) AI-004 แนะนำให้เพิ่มคิวจำกัดขนาดหน้า Ollama ซึ่ง **ยังไม่ได้ทำ** ต้องรอการอนุมัติ (ดู `docs/BE-003-CONFIGURATION.md` ข้อ 2a/2b)

คำขอที่มาพร้อมกันเข้าคิวที่ Ollama ตัว `HttpClient` รอได้ไม่เกิน `Ollama:TimeoutSeconds` (ค่าเริ่มต้น 180 วินาที)
แล้วตอบ **504 `AI_TIMEOUT`**

| การทดสอบ (กับ Ollama จริง) | ผล |
|----------------------------|-----|
| 5 คำขอพร้อมกัน, คำตอบสั้น | สำเร็จทั้งหมด ช้าสุด 0.9 วินาที |
| 30 คำขอพร้อมกัน, คำตอบสั้น | สำเร็จ 30/30, ช้าสุด 5.6 วินาที |
| 10 คำขอพร้อมกัน, คำตอบ 3 ประโยค | สำเร็จ 10/10, เวลารวม 26 วินาที, ช้าสุด 26 วินาที (ประมาณ 2.6 วินาที/คำขอ) |
| 15 คำขอพร้อมกัน, คำตอบ 3 ประโยค, timeout ตั้ง 12 วินาที | สำเร็จ 4, ได้ 504 จำนวน 11 ตัว |
| คำขอ 3 ข้อความสั้น ๆ หลังโหลดเกิน | สำเร็จทั้งหมดใน 0.7 วินาที (ระบบกลับมาปกติทันที ไม่ค้าง) |

ข้อสรุปที่วัดได้: เมื่อโหลดเกินความสามารถ ระบบ **ไม่พัง** แต่ตอบ 504 ตามสัญญาแล้วกลับมาปกติ

**ประมาณการ (ไม่ได้ทดสอบ):** ที่ ~2.6 วินาทีต่อคำตอบปานกลาง ภายใน 180 วินาทีรองรับได้ราว 70 คำขอที่ส่งพร้อมกัน
ถ้า 100 คนส่งคำถามยาวปานกลางในเวลาเดียวกัน คำขอท้ายคิวจะได้ 504 ตัวเลขนี้ขึ้นกับ GPU จึงต้องวัดซ้ำบนเครื่องเป้าหมาย
(ผู้ใช้ 40–100 คนไม่ได้ส่งพร้อมกันทั้งหมด การใช้งานจริงควรวัดด้วยโหลดจริง)

**BE-008:** ตัวจำกัดคำขอและคิวมีขอบเขตที่ Backend ทำแล้ว (`ChatQueue`, ดู [BE-008-CONFIGURATION.md](BE-008-CONFIGURATION.md)) ตัวเลขข้างบนวัดก่อน BE-008 ข้อจำกัดที่ยังเหลือ:
- ค่าเริ่มต้น (parallel 1, คิว 8, รอ 30 s, 1 คำขอค้างต่อผู้ใช้) เป็นข้อเสนอจาก AI-006/AI-007 ยังไม่ได้รับอนุมัติและยังไม่ได้วัดโหลดบนเครื่องเป้าหมาย
- ตำแหน่งในคิวเป็น snapshot ตอนรับคำขอ ไม่มีเวลารอโดยประมาณ (event `queued`/`processing` ปิดอยู่จนกว่า FE-004 ยอมรับสัญญา)
- คิวอยู่ใน memory ของโปรเซสเดียว ไม่รองรับหลายอินสแตนซ์
- เมื่อ `Authentication:Enabled=false` ทุกคนใช้โควตาเดียวกัน (1 คำขอค้างทั้งระบบ) จึงต้องตั้ง `ChatQueue:MaxPendingPerUser` เมื่อทดสอบหลายคำขอพร้อมกันในโหมดนั้น

ทางเลือกที่ยังไม่ได้ทำ: ปรับ `OLLAMA_NUM_PARALLEL` (ดู AI-006), หรือใช้ GPU ที่แรงกว่า

## 3. ไม่มี conversation history; หน้าเว็บเดิมยังไม่ใช้ Streaming API

ทุกคำถามเป็นอิสระต่อกัน โมเดลไม่จำคำถามก่อนหน้า และผู้ใช้เห็นคำตอบเมื่อโมเดลเขียนเสร็จทั้งหมด
BE-004 เพิ่ม `POST /api/chat/stream` แล้ว (ดู [SSE contract](BE-004-SSE-CONTRACT.md)) ส่วนการนำมาใช้บนหน้าเว็บอยู่ใน FE-002
และ conversation history อยู่ใน BE-007

## 4. ไม่มี Authentication / rate limit

`/api/chat` เปิดให้เรียกได้โดยไม่ต้องยืนยันตัวตนเมื่อ `Authentication:Enabled=false` (ค่าเริ่มต้น) ควรใช้งานเฉพาะในเครือข่ายภายในจนกว่าจะเปิด Authentication
BE-008 จำกัดคำขอค้างต่อผู้ใช้ที่ยืนยันตัวตนแล้ว (ค่าเริ่มต้น 1) ไม่ใช่ rate limit ต่อเวลา และไม่จำกัดจำนวนคำถามที่ถามต่อเนื่อง

ไม่มีการจำกัดความยาวข้อความของผู้ใช้ในโค้ด ข้อความ 200 KB ส่งได้และตอบปกติใน 1.5 วินาที (วัดจริง)
ขีดจำกัดอื่นขึ้นกับ Kestrel และ context ของโมเดล ซึ่งยังไม่ได้ตรวจเพิ่ม

## 5. สัญญา Ollama ยังไม่ได้รับการอนุมัติ

Issue #5 (AI-002) และ PR #8 ยังเปิดอยู่และยังไม่มีการอนุมัติ งานนี้ทำตามเอกสารสัญญาใน PR #8 (`docs/ai/ollama-integration-contract.md`) ซึ่งตรงกับ Issue #5 ทุกจุด ยกเว้น system prompt ที่ใช้ฉบับใน PR #8 (ตอบภาษาเดียวกับผู้ใช้) ถ้า Backend Developer / Tech Lead
ขอเปลี่ยน (เช่น `num_predict`, system prompt) ต้องแก้ `OllamaGenerateRequest` และเทสต์ที่เกี่ยวข้อง

## พฤติกรรมอื่นที่ทดสอบแล้ว (ไม่ใช่ข้อจำกัด)

- **Ollama เข้าถึงผ่าน loopback เท่านั้น (บังคับตอนเริ่มระบบ):** `Ollama:BaseUrl` ต้องเป็น URL แบบ http/https ที่ชี้ loopback
  (`127.0.0.1`, `localhost`, `[::1]`) ถ้าตั้งเป็น `https://ollama.internal:11434`, `http://192.168.1.10:11434`,
  `https://ollama.example.com` หรือ `http://0.0.0.0:11434` แอปจะเปิดไม่ขึ้นพร้อมข้อความ
  `Ollama:BaseUrl must be an absolute loopback http or https URL.` (ทดสอบกับแอปจริงแล้ว)
  หมายเหตุ: `http://[::1]:11434` ผ่านการตรวจ แต่ Ollama บนเครื่องที่ทดสอบฟังเฉพาะ IPv4 `127.0.0.1` จึงได้ 503 `AI_UNAVAILABLE`
  ถ้าต้องใช้ IPv6 ต้องตั้ง Ollama ให้ฟัง `::1` ด้วย

- อีโมจิและอักขระนอก BMP ส่งถึง Ollama ครบถ้วน (ตอบ 200)
- JSON ที่ผู้ใช้พิมพ์เป็นข้อความ และข้อความที่ล่อให้โมเดลพิมพ์ `<think>` ไม่ทำให้ API พัง
- อักขระ surrogate เดี่ยวที่ไม่ถูกต้อง -> 400 `INVALID_MESSAGE`
- ผู้ใช้ตัดการเชื่อมต่อกลางทาง -> ไม่มี error, คำขอถัดไปทำงานปกติ
- โมเดลที่ระบุไม่ได้ติดตั้ง -> 502 `AI_PROVIDER_ERROR`; Ollama ไม่รันอยู่ -> 503 `AI_UNAVAILABLE`
