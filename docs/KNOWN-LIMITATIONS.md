# ข้อจำกัดที่ทราบ (Known Limitations) — BE-002 Ollama Integration

เอกสารนี้สรุปข้อจำกัดของ `/api/chat` ที่เชื่อมกับ Ollama (`qwen3:4b`) เพื่อให้ผู้รีวิวตัดสินใจก่อน merge
แต่ละข้อระบุว่า **วัดจริง** หรือ **ประมาณการ** อย่างชัดเจน

ทดสอบวันที่ 2026-10-19 บนเครื่องพัฒนา: Windows 11, NVIDIA RTX 4050 Laptop (VRAM 6 GB), Ollama กับ `qwen3:4b`
(เครื่องนี้ไม่ใช่สเปกเป้าหมาย RTX 4060/4070 ตามที่ AI-001 บันทึกไว้ ตัวเลขความเร็วจึงใช้เทียบเคียงเท่านั้น)

## สรุปสั้น

| # | ข้อจำกัด | ผลกระทบต่อผู้ใช้ | สถานะ |
|---|----------|------------------|--------|
| 1 | คำตอบยาวเกิน 256 token ถูกตัด | ได้ error 502 แทนคำตอบ | วัดจริง |
| 2 | Ollama ตอบทีละคำขอ (เข้าคิว) | คนจำนวนมากพร้อมกันรอนานหรือได้ 504 | วัดจริงที่ 5–30 คำขอ, ส่วน 100 คนเป็นประมาณการ |
| 3 | ไม่มี conversation history และไม่ streaming | ถามตอบทีละข้อ ไม่จำบริบท ได้คำตอบเมื่อเสร็จทั้งหมด | ตามขอบเขต Issue #6 |
| 4 | ไม่มี Authentication / rate limit | ใครเรียก API ได้ก็ใช้ GPU ได้ | นอกขอบเขต (issue แยก) |
| 5 | สัญญา Ollama (Issue #5) ยังไม่มีการอนุมัติเป็นลายลักษณ์อักษร | อาจต้องแก้ถ้า Tech Lead เปลี่ยนสัญญา | รอคน |
| 6 | ระบบไม่บังคับให้ `Ollama:BaseUrl` เป็น loopback | ตั้งค่าชี้เครื่องอื่นได้ ต้องไม่เปิด Ollama สู่อินเทอร์เน็ต | ตามการออกแบบ |

## 1. คำตอบยาวเกิน 256 token ได้ 502 (วัดจริง)

สัญญา AI-002 กำหนด `num_predict = 256` ถ้าโมเดลเขียนไม่จบภายใน 256 token Ollama จะหยุดและรายงาน
`done_reason = "length"` ซึ่งสัญญาถือว่าไม่สำเร็จ API จึงตอบ **502 `AI_INVALID_RESPONSE`** แทนที่จะส่งคำตอบครึ่งเดียว

- ตัวอย่างจริง: ถาม "เขียนเรียงความยาวมาก ไม่น้อยกว่า 1500 คำ เรื่องประวัติศาสตร์ประเทศไทย" -> 502 ใน 4.6 วินาที
- คำถามที่ตอบสั้น (คำนวณ, คำถามข้อเท็จจริง, สรุป 3 ประโยค) ผ่านปกติ
- ทางแก้ (ยังไม่ได้ทำ ต้องให้ Tech Lead อนุมัติ): เพิ่ม `num_predict` ในสัญญา หรือยอมรับคำตอบที่ถูกตัดพร้อมสัญญาณบอกผู้ใช้
- ข้อเสนอ: UI ควรแนะนำให้ผู้ใช้ถามสั้น ๆ และแสดงข้อความเข้าใจง่ายเมื่อได้ `AI_INVALID_RESPONSE`

## 2. Ollama ประมวลผลทีละคำขอ (วัดจริง + ประมาณการ)

คำขอที่มาพร้อมกันเข้าคิวที่ Ollama ตัว `HttpClient` รอได้ไม่เกิน `Ollama:TimeoutSeconds` (ค่าเริ่มต้น 180 วินาที)
แล้วตอบ **504 `AI_TIMEOUT`**

| การทดสอบ (กับ Ollama จริง) | ผล |
|----------------------------|-----|
| 5 คำขอพร้อมกัน, คำตอบสั้น | สำเร็จทั้งหมด ช้าสุด 0.9 วินาที |
| 30 คำขอพร้อมกัน, คำตอบสั้น | สำเร็จ 30/30, ช้าสุด 5.6 วินาที |
| 10 คำขอพร้อมกัน, คำตอบ 3 ประโยค | สำเร็จ 10/10, เวลารวม 26 วินาที, ช้าสุด 26 วินาที (ประมาณ 2.6 วินาที/คำขอ) |
| 15 คำขอพร้อมกัน, คำตอบ 3 ประโยค, timeout ตั้ง 12 วินาที | สำเร็จ 4, ได้ 504 จำนวน 11 ตัว |
| คำขอ 3 ข้อความสั้น ๆ หลังโหลดเกิน | สำเร็จทั้งหมดใน 0.7 วินาที (ระบบกลับมาปกติทันที ไม่ค้าง) |

ข้อสรุปที่วัดได้: เมื่อโหลดเกินความสามารถ ระบบ **ไม่พัง** แต่ตอบ 504 ตามสัญญาแล้วกลับมาปกติ

**ประมาณการ (ไม่ได้ทดสอบ):** ที่ ~2.6 วินาทีต่อคำตอบปานกลาง ภายใน 180 วินาทีรองรับได้ราว 70 คำขอที่ส่งพร้อมกัน
ถ้า 100 คนส่งคำถามยาวปานกลางในเวลาเดียวกัน คำขอท้ายคิวจะได้ 504 ตัวเลขนี้ขึ้นกับ GPU จึงต้องวัดซ้ำบนเครื่องเป้าหมาย
(ผู้ใช้ 40–100 คนไม่ได้ส่งพร้อมกันทั้งหมด การใช้งานจริงควรวัดด้วยโหลดจริง)

ทางเลือก (ยังไม่ได้ทำ): จำกัดจำนวนคำขอพร้อมกันที่ฝั่ง Backend, แสดงตำแหน่งในคิว, ปรับ `OLLAMA_NUM_PARALLEL`, หรือใช้ GPU ที่แรงกว่า

## 3. ไม่มี conversation history และไม่ streaming

ทุกคำถามเป็นอิสระต่อกัน โมเดลไม่จำคำถามก่อนหน้า และผู้ใช้เห็นคำตอบเมื่อโมเดลเขียนเสร็จทั้งหมด
ทั้งสองอย่างอยู่นอกขอบเขต Issue #6 (Out of Scope)

## 4. ไม่มี Authentication / rate limit

`/api/chat` เปิดให้เรียกได้โดยไม่ต้องยืนยันตัวตน และไม่จำกัดจำนวนคำขอต่อผู้ใช้ Authentication ถูกระบุว่าเป็น issue แยก
ควรใช้งานเฉพาะในเครือข่ายภายในจนกว่าจะมี Authentication

ไม่มีการจำกัดความยาวข้อความของผู้ใช้ในโค้ด ข้อความ 200 KB ส่งได้และตอบปกติใน 1.5 วินาที (วัดจริง)
ขีดจำกัดอื่นขึ้นกับ Kestrel และ context ของโมเดล ซึ่งยังไม่ได้ตรวจเพิ่ม

## 5. สัญญา Ollama ยังไม่ได้รับการอนุมัติ

Issue #5 (AI-002) ยังเปิดอยู่และไม่มีคอมเมนต์อนุมัติ งานนี้ทำตามสัญญาที่เขียนไว้ใน issue นั้น ถ้า Backend Developer / Tech Lead
ขอเปลี่ยน (เช่น `num_predict`, system prompt) ต้องแก้ `OllamaGenerateRequest` และเทสต์ที่เกี่ยวข้อง

## 6. `Ollama:BaseUrl` ไม่ถูกบังคับให้เป็น loopback

ค่าเริ่มต้นคือ `http://127.0.0.1:11434` และ Ollama บนเครื่องที่ทดสอบฟังเฉพาะ `127.0.0.1:11434` (ตรวจแล้ว)
แต่การตั้งค่าตรวจเพียงว่าเป็น URL แบบ http/https ที่ถูกต้อง ผู้ดูแลจึงตั้งให้ชี้เครื่องอื่นได้
ห้ามเปิด Ollama API สู่อินเทอร์เน็ตสาธารณะ ถ้าต้องการให้ระบบปฏิเสธ URL ที่ไม่ใช่ loopback ต้องเพิ่มกติกาใน `OllamaOptionsValidator`

## พฤติกรรมอื่นที่ทดสอบแล้ว (ไม่ใช่ข้อจำกัด)

- อีโมจิและอักขระนอก BMP ส่งถึง Ollama ครบถ้วน (ตอบ 200)
- JSON ที่ผู้ใช้พิมพ์เป็นข้อความ และข้อความที่ล่อให้โมเดลพิมพ์ `<think>` ไม่ทำให้ API พัง
- อักขระ surrogate เดี่ยวที่ไม่ถูกต้อง -> 400 `INVALID_MESSAGE`
- ผู้ใช้ตัดการเชื่อมต่อกลางทาง -> ไม่มี error, คำขอถัดไปทำงานปกติ
- โมเดลที่ระบุไม่ได้ติดตั้ง -> 502 `AI_PROVIDER_ERROR`; Ollama ไม่รันอยู่ -> 503 `AI_UNAVAILABLE`
