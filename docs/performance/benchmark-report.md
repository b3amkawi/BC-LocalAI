## 2. ขอบเขตและสถานะของผล

- ทดสอบวันที่ 20 ตุลาคม 2026 ครบ **24 scenarios** (4 ระดับ concurrency × 3 profile × 2 เป้าหมาย) รวม **3,156 คำขอที่วัดผล** (Direct 1,578 + Backend 1,578) ไม่มี safety stop ในรอบสุดท้าย และ RAM ไม่เคยต่ำกว่าเกณฑ์ (ไม่ต้องรอฟื้นเลย: `memory_pauses` = 0)
- **จำนวนตัวอย่างต่อ scenario อยู่ที่ 125–150 คำขอ และคำขอที่สำเร็จ ≥ 100 ในทุก scenario** จึงรายงาน P99 ได้ตามเงื่อนไขของ Issue (ต้องมีตัวอย่างเพียงพอและรายงาน Sample Size) ตาราง n แสดงจำนวนตัวอย่างที่สำเร็จ
- ที่ยังต้องเรียกว่า **Baseline ไม่ใช่ข้อสรุปความสามารถรองรับโหลดจริง** ตามที่ Issue กำหนด: ใช้เครื่องเดียว (laptop) ที่เปิดโปรแกรมอื่นอยู่, ยิงแบบ burst พร้อมกันไม่ใช่ผู้ใช้จริงที่มาแบบสุ่ม, ไม่ได้ทดสอบเกิน 10 พร้อมกัน และ cold start มี 5 ตัวอย่าง
- ตัวเลขใดที่เป็นประมาณการ ไม่ได้วัด จะเขียนกำกับว่า "ประมาณการ"
- **ผลนี้เป็น baseline ก่อน BE-003** Backend ที่ทดสอบยังใช้ `num_predict=256` ตายตัว (PR #19 ของ BE-003 เปลี่ยนเป็น `MaxOutputTokens=1024` และเพิ่ม `AI_RESPONSE_TOO_LARGE`) ควรรันซ้ำหลัง merge

### 6.2 อ่านผลอย่างไร (ตรงกับหลักฐาน)

- **medium และ long ไม่ต่างกันอย่างมีนัย:** P50 ต่างกันภายใน ±6% และ throughput ต่างไม่เกิน 1% **ยกเว้น long c=2 (+29%)** ซึ่งเป็นผลจากรูปแบบการกระจายตัว: latency ของ long ที่ c=2 แบ่งเป็นสองกลุ่ม (≈ 2.3 วินาทีและ ≈ 4.2 วินาที ตามลำดับคิว) ค่า P50 จึงตกอยู่ตรงรอยต่อและไวต่อการสลับเพียงไม่กี่คำขอ ส่วน P95 ต่างกันแค่ 2% (6,426 กับ 6,526) และ P50 ของ Direct เองเปลี่ยนจาก 2,425 ms (รอบสำรวจ) เป็น 3,257 ms (รอบสุดท้าย)
- **short ที่ c ≤ 5: Backend สูงกว่า 11–20% (+26 ถึง +137 ms) และ throughput ต่ำกว่า 9–15%** ที่ c=10 ต่างเพียง +1% / −2%
- **แต่ความแปรผันระหว่างรอบของเครื่องนี้ใหญ่พอ ๆ กัน:** P50 ของ Direct short c=1 ที่วัดได้ในสี่รอบที่รันคือ 289, 273, 283 และ 231 ms (ต่างกัน 25%) ขณะที่ Backend ที่วัดสองรอบเต็ม (รอบแรกที่เก็บเป็นหลักฐานกับรอบสุดท้าย) ต่างกันสูงสุด ±16% (ตาราง 6.3) รอบที่ Direct เร็วที่สุด (231 ms) ถูกวัดตอนเครื่องว่างกว่า จึงเปรียบเทียบกับ Backend ที่วัดคนละช่วงเวลาไม่ได้อย่างยุติธรรม
- **ข้อสรุป:** Backend ไม่ได้เพิ่มเวลาในระดับที่กระทบการตัดสินใจ ขอบบนของ overhead ที่เป็นไปได้คือราว **+26–137 ms ต่อคำขอ short** (เทียบกับ cold/medium/long ที่เป็นวินาที) แต่ **วัดไม่ได้ว่าส่วนนี้เป็น overhead จริงของ Backend หรือความแปรผันของรอบ** วิธีแยกคือรัน Direct และ Backend สลับกันภายในรอบเดียวกัน ซึ่ง AI-004 ยังไม่ได้ทำ ไม่ว่าอย่างไรคอขวดอยู่ที่ Ollama/GPU ไม่ใช่ Backend

- **VRAM ใช้คงที่ 3,158 MB จาก 6,141 MB** ไม่เปลี่ยนตาม concurrency (โมเดลโหลดครั้งเดียว และ `NUM_PARALLEL=1`) ยังเหลือราว 3 GB
- **CPU ไม่ใช่คอขวดโดยเฉลี่ย** (15–42%) แต่มีช่วงพุ่งถึง 99–100% ที่ long c=5 และ c=10 (เป็นการพุ่งชั่วครู่ ค่าเฉลี่ยยังอยู่ที่ราว 19–23%)
- **RAM:** process ของ Ollama รวม runner (`llama-server.exe` ที่ถือหน่วยความจำฝั่ง CPU ของโมเดล) ใช้ 0.85–1.7 GB ซึ่งเป็นส่วนหนึ่งที่ทำให้ RAM ว่างของเครื่อง 16 GB ที่เปิดโปรแกรมอื่นอยู่ลดลง ต่ำสุดที่วัดได้ **606 MB** ที่ medium c=10 ของ Direct ยังสูงกว่าเกณฑ์ 512 MB จึงไม่เกิดการหยุดหรือรอเลย

## 8. Bottleneck Analysis

### 8.1 Ollama ประมวลผลทีละคำขอ ทำให้ latency เพิ่มตามความยาวคิว (วัดจริง)

throughput แทบคงที่เมื่อ concurrency เพิ่มจาก 1 เป็น 10 (medium 0.74 → 0.69 คำขอ/วินาที, long 0.29 → 0.29) ขณะที่ P50 ของ medium เพิ่มจาก 1.3 เป็น 7.8 วินาที และ queue wait P95 ที่ c=10 คือ 2.0 / 13.4 / 25.1 วินาที (short/medium/long) ซึ่งเกือบเท่า latency ทั้งหมด แปลว่าเวลาส่วนใหญ่ของคำขอที่ concurrency สูงคือการรอคิว สอดคล้องกับ `OLLAMA_NUM_PARALLEL=1` ที่อ่านจาก log ของ Ollama ผลคือ **การส่งคำขอเข้า Ollama พร้อมกันมากขึ้นไม่ได้เพิ่มงานที่เสร็จต่อวินาที** มีแต่ทำให้ผู้ใช้แต่ละคนรอนานขึ้น

### 8.2 คำตอบถูกตัดที่ 256 token ทำให้ Backend ตอบ 502 (วัดจริง, deterministic)

ใน profile long มี 3 prompt ที่ **ถูกตัดที่ `done_reason=length` (`eval_count=256`) ทุกครั้ง: `long-3`, `long-11`, `long-14` ซึ่งเป็น prompt ภาษาไทยทั้งสามข้อ (35 ครั้งต่อข้อ รวม 105 จาก 105 ครั้ง)** และ Backend ตอบ 502 `AI_INVALID_RESPONSE` ทุกครั้งเช่นกัน (105 จาก 105) prompt ที่เหลืออีก 12 ข้อ (ภาษาอังกฤษทั้งหมด) จบปกติทุกครั้งด้วย 119–196 token (มัธยฐาน 136) ส่วน 3 ข้อภาษาไทยต้องการเกิน 256 token แปลว่าอัตรา 80% ของ long ไม่ใช่ความไม่เสถียรของระบบ แต่เป็นคำถามภาษาไทยที่ใช้ token เกินงบ ซึ่งภาษาไทยใช้ token ต่อคำมากกว่าอังกฤษ ตรงกับข้อจำกัดข้อ 1 ใน `docs/KNOWN-LIMITATIONS.md` และเป็นข้อมูลโดยตรงสำหรับ BE-003

ข้อควรระวัง: เรามี prompt ภาษาไทยในชุดทดสอบเพียง 9 ข้อจาก 45 (3 ข้อต่อ profile) ข้อสรุปที่ว่า "ภาษาไทยถูกตัดทุกครั้ง" มีหลักฐานเฉพาะ profile long ที่ขอย่อหน้า ≈ 120 คำ ไม่ได้แปลว่าคำตอบภาษาไทยทุกคำถามจะถูกตัด

### 8.3 GPU คือทรัพยากรที่จำกัดความเร็วของคำตอบยาว (วัดจริง)

GPU ≈ 90% ที่ long และความเร็ว generate ≈ 60 tokens/s คงที่ ความเร็วต่อคำขอจึงถูกจำกัดด้วย GPU ของเครื่องนี้ การเพิ่ม concurrency ไม่ช่วย (8.1) การเพิ่ม `OLLAMA_NUM_PARALLEL` อาจช่วยได้เพราะยังเหลือ VRAM ราว 3 GB แต่ **ยังไม่ได้ทดสอบ** (การปรับ config ของ Ollama อยู่นอกขอบเขต AI-004)

### 8.4 ขีดจำกัดของ Backend timeout 180 วินาที (ประมาณการ ไม่ได้วัด)

ไม่มีคำขอใดเกิน 28.7 วินาที จึงยังไม่เคยเห็น 504 `AI_TIMEOUT` ประมาณการจาก throughput ที่วัดได้: คำขอลำดับที่ N ในคิวรอประมาณ N ÷ throughput วินาที ภายใน 180 วินาทีคิวจึงรองรับได้ราว **760 (short), 124 (medium), 52 (long)** คำขอที่ส่งพร้อมกัน ก่อนที่ตัวท้ายคิวจะได้ 504 ตัวเลขนี้สมมติว่าการรอคิวเป็นเส้นตรงและเครื่องไม่ throttle ที่โหลดสูง ซึ่งไม่ได้ทดสอบ และผู้ใช้จริงไม่น่ารอได้ถึง 180 วินาที ที่เป้าหมายรอไม่เกิน 30 วินาที รองรับพร้อมกันราว 20 คำขอ medium (ประมาณการ)

### 8.5 สิ่งที่ไม่ใช่คอขวด

- VRAM ยังเหลือ (ใช้ 3.2 จาก 6.1 GB) และ CPU เฉลี่ยต่ำ (ข้อ 7)
- Backend: overhead ที่เป็นไปได้ไม่เกินราว +137 ms ต่อคำขอ short และ ≤ ~6% ที่ medium/long (ข้อ 6)

## 11. Known Limitations

- **เครื่องเดียว** (laptop RTX 4050 6 GB, RAM 15.6 GiB ที่มีโปรแกรมอื่นเปิดอยู่) ไม่ใช่เครื่องเป้าหมาย RTX 4060/4070 ตามที่ AI-001 บันทึกไว้ ตัวเลขสัมบูรณ์ใช้กับเครื่องอื่นไม่ได้ ใช้ได้เฉพาะรูปแบบพฤติกรรม
- **ความแปรผันระหว่างรอบ:** short แปรผันได้ถึง 16–25% ระหว่างรอบ (ข้อ 6.2–6.3) การเปรียบเทียบ Direct กับ Backend ทำคนละช่วงเวลา ไม่ได้สลับสุ่มลำดับ จึงสรุป overhead ของ Backend ที่ระดับ ±20% ของ short ไม่ได้
- **ชุด prompt 45 ข้อ** ไม่ได้เป็นตัวแทนคำถามของผู้ใช้จริง มีภาษาไทยเพียง 9 ข้อ และ 3 ข้อใน long ถูกตัดแบบ deterministic ทำให้ success ของ long คือ 80% พอดี
- **ยิงแบบ burst** (ทุกคำขอในรอบเริ่มพร้อมกัน) ไม่ใช่การมาถึงแบบสุ่ม **ไม่ได้ทดสอบเกิน 10 พร้อมกัน** ไม่ได้ทดสอบ 504 จริง ไม่ได้ทดสอบการยกเลิกคำขอ และไม่ได้ทดสอบ `NUM_PARALLEL` ที่ต่างจาก default
- **ไม่ได้วัด time-to-first-token** (ไม่มี streaming ใน contract ปัจจุบัน)
- Queue wait เป็นค่าคำนวณจาก elapsed − (load + prompt eval + generate) ที่ Ollama รายงาน ไม่ใช่ค่าที่ Ollama รายงานตรง ๆ
- Cold start มี 5 ตัวอย่างต่อเป้าหมาย (ไม่ใช่ cold boot ของเครื่อง)
- ค่าประมาณขีดจำกัดของคิว (ข้อ 8.4) เป็นการประมาณ ไม่ได้ทดสอบ
- ไม่มีการเปลี่ยน configuration ของ Ollama หรือ Backend ระหว่างทดสอบ (มีเพียงการสั่ง `ollama stop` ก่อนวัด cold start)
