# AI-004: Performance Report (D4)

รายงานผล benchmark ของ Ollama + `qwen3:4b` และ Backend `POST /api/chat` วิธีวัด สภาพแวดล้อม และคำนิยาม metrics อยู่ใน [Benchmark Test Plan](benchmark-plan.md) สิ่งที่ต้องนำไปใช้ใน BE-003/BE-004 สรุปไว้ใน [Handoff](benchmark-handoff.md)

## สถานะ: Preliminary Results

ทุก scenario มีตัวอย่าง 4–50 ตัว (ไม่ถึง 100) จึง **ไม่ใช่ข้อสรุปความสามารถรองรับโหลดจริง** และ **P99 ใช้ตัดสินใจไม่ได้** (คอลัมน์ P99 ในตารางเท่ากับค่าสูงสุดเกือบทุกแถว) ตัวเลขใช้บอกรูปแบบพฤติกรรมและเปรียบเทียบ Direct กับ Backend บนเครื่องเดียวกันเท่านั้น ข้อที่เป็นประมาณการ ไม่ได้วัด จะระบุว่า "ประมาณการ" ทุกครั้ง

ทดสอบวันที่ 20 ตุลาคม 2026 (Ollama Direct 10:43–10:50 น., Backend 10:50–10:57 น. เวลา Asia/Bangkok) ครบ 24 scenarios (4 concurrency × 3 profile × 2 เป้าหมาย) รวม 540 คำขอที่วัดผล ไม่มี safety stop และไม่มี client/server timeout เลยตลอดการทดสอบ

## 6. Bottleneck Analysis (อ้างอิงหลักฐาน)

### 6.1 คำตอบถูกตัดที่ 256 token ทำให้ Backend ตอบ 502 (วัดจริง, deterministic)

ใน profile long คำขอ 1 ใน 5 prompt คือ `long-3` (ขอย่อหน้าภาษาไทยประมาณ 120 คำ) **ถูกตัดที่ `done_reason=length`, `eval_count=256` ทุกครั้ง (18 จาก 18 ครั้งใน Direct)** และ Backend ตอบ 502 `AI_INVALID_RESPONSE` ทุกครั้ง (18 จาก 18) 4 ใน 5 prompt ที่เหลือใช้ ≈ 137 token (ภาษาอังกฤษ ≈ 720 ตัวอักษร) แล้วจบปกติ แปลว่าอัตรา 80% ไม่ใช่ความไม่เสถียรของระบบ แต่เป็นคำถามที่ต้องใช้ token เกินงบ ซึ่งภาษาไทยกินจำนวน token ต่อคำมากกว่าอังกฤษ นี่ตรงกับข้อจำกัดข้อ 1 ใน `docs/KNOWN-LIMITATIONS.md` และเป็นข้อมูลโดยตรงสำหรับ BE-003 (ดู Handoff)

### 6.2 Ollama ประมวลผลทีละคำขอ ทำให้ latency เพิ่มตามความยาวคิว (วัดจริง)

**หลักฐาน:** throughput คงที่ไม่ว่ายิงพร้อมกันกี่ตัว (short 3.42 → 3.47 req/s, medium 0.68 → 0.66, long 0.30 → 0.30 เมื่อ concurrency เพิ่มจาก 1 เป็น 10) ในขณะที่ P50 ของ medium เพิ่มจาก 1.3 s เป็น 7.5 s และ queue wait P95 ที่ c=10 อยู่ที่ 2.6 / 13.6 / 24.0 วินาที (short/medium/long) ซึ่งเกือบเท่า latency ทั้งหมด แปลว่าเวลาส่วนใหญ่ของคำขอที่ concurrency สูงคือการรอคิว ไม่ใช่การประมวลผล สอดคล้องกับ `OLLAMA_NUM_PARALLEL=1` ที่อ่านจาก log ของ Ollama และกับข้อ 2 ของ `KNOWN-LIMITATIONS.md`

**ผลที่ตามมา:** การยิงเข้า Ollama พร้อมกันมากขึ้น **ไม่เพิ่มงานที่เสร็จต่อวินาที** มีแต่ทำให้ผู้ใช้แต่ละคนรอนานขึ้น

### 6.3 GPU คือทรัพยากรที่จำกัดความเร็วของคำตอบยาว (วัดจริง)

GPU ≈ 90% ที่ medium/long, ความเร็ว generate ≈ 60 tokens/s คงที่ จึงแปลว่าความเร็วต่อคำขอถูกจำกัดด้วย GPU ของเครื่องนี้ การเพิ่ม concurrency ไม่ช่วย (6.2) การเพิ่ม `NUM_PARALLEL` อาจช่วยได้บ้างเพราะยังมี VRAM เหลือราว 3 GB แต่ **ยังไม่ได้ทดสอบ** (การปรับ config ของ Ollama อยู่นอกขอบเขต AI-004)

### 6.4 ขีดจำกัดของ Backend timeout 180 วินาที (ประมาณการ ไม่ได้วัด)

ไม่มีคำขอใดเกิน 27 วินาที จึงยังไม่เคยเห็น 504 `AI_TIMEOUT` ในการทดสอบนี้ ประมาณการจาก throughput ที่วัดได้: คำขอลำดับที่ N ในคิวรอประมาณ N ÷ throughput วินาที ดังนั้นภายใน 180 วินาทีคิวรองรับได้ราว **620 คำขอ (short), 120 (medium), 54 (long)** ที่ส่งพร้อมกัน ก่อนที่ตัวท้ายคิวจะได้ 504 ตัวเลขนี้สมมติว่าการรอคิวเป็นเส้นตรงและเครื่องไม่ throttle ที่โหลดสูง ซึ่งไม่ได้ทดสอบ และผู้ใช้จริงไม่น่าจะรอได้ถึง 180 วินาที เช่น ที่เป้าหมายรอไม่เกิน 30 วินาที รองรับพร้อมกันราว 20 คำขอ medium (ประมาณการ)

### 6.5 สิ่งที่ไม่ใช่คอขวด

- Backend ไม่เพิ่ม overhead ที่วัดได้ (ข้อ 5)
- CPU และ VRAM ยังเหลือ (ข้อ 5)

## 8. Known Limitations

- **ตัวอย่างน้อย (n ≤ 50 ต่อ scenario) จึงเป็น Preliminary** และ P99 ไม่น่าเชื่อถือ; cold start วัดครั้งเดียวต่อเป้าหมาย
- เครื่องเดียว (laptop RTX 4050 6 GB, RAM 16 GB ที่มีโปรแกรมอื่นเปิดอยู่) ไม่ใช่เครื่องเป้าหมาย ตัวเลขสัมบูรณ์ใช้กับเครื่องอื่นไม่ได้ ใช้ได้เฉพาะรูปแบบพฤติกรรม
- ผลเปรียบเทียบ Direct/Backend ทำคนละช่วงเวลา (ห่างกัน 7 นาที) ไม่ได้สลับสุ่มลำดับ
- ใช้ prompt ชุดเล็กที่กำหนดไว้ล่วงหน้า (15 prompt, ภาษาไทย 3) ไม่ได้เป็นตัวแทนคำถามของผู้ใช้จริง และ `long-3` ที่ถูกตัดทำให้ผล long มี Success 80% แบบ deterministic
- ทุกคำขอในรอบหนึ่งเริ่มพร้อมกัน (burst) ไม่ใช่การมาถึงแบบสุ่มของผู้ใช้จริง
- ไม่ได้วัด time-to-first-token (ไม่มี streaming), ไม่ได้ทดสอบ concurrency เกิน 10, ไม่ได้ทดสอบ timeout 504 จริง, ไม่ได้ทดสอบการยกเลิกคำขอ และไม่ได้ทดสอบ `NUM_PARALLEL` ที่ต่างจาก default
- ตัวเลข queue wait คำนวณจาก elapsed − (load + prompt eval + generate) ที่ Ollama รายงาน เป็นค่าประมาณ ไม่ใช่ค่าที่ Ollama รายงานตรง ๆ นิยามเดิม (elapsed − `total_duration`) ผิดเพราะ `total_duration` รวมเวลารอคิวไว้แล้ว จึงแก้สคริปต์และคำนวณคอลัมน์นี้ใหม่จากค่าดิบเดิมใน CSV (ค่าดิบทุกคอลัมน์ไม่ถูกแก้)
- ไม่มีการเปลี่ยน configuration ของ Ollama หรือ Backend ระหว่างทดสอบ
